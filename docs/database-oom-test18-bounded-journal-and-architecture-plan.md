## 2. Как раньше хранился журнал и почему он рос

- TEST_13–17 использовали общую IndexedDB `ReclassifierDiagnosticHistoryV13` и ключи `reclassifier.diagnostic-wal.v13.*` в localStorage браузерного профиля. Привязки к конкретному файлу HTML не было.
- Каждая новая сборка с новым `testLabel` создавала новые сессии **в том же архиве**, а `collect('runtime')` выгружал всё, что там накопилось.
- Каждое `runtime-cache/progress` при попадании в кэш порождало событие, маленький WAL и IndexedDB транзакцию. Сессия с 54k попаданий сама способна создавать существенную нагрузку на приложение.
- Удалять старую IndexedDB автоматически при тестировании опасно: она содержит диагностические данные для сравнений. Поэтому новый TEST_18 создаёт **другой namespace** и старый оставляет нетронутым.

## 3. Реализация TEST_18

1. `ReclassifierDiagnosticScope`: объединяет `RECLASSIFIER_BUILD.testLabel` и **путь открытого HTML (`location.pathname`)**, выдаёт стабильный fingerprint; в интерфейсе и JSON отображает только имя файла, не полный локальный путь. Файлы с одинаковыми именами в разных папках получают разные журналы. Связывает с ним отдельные IndexedDB, WAL, V2 checkpoint и UI ring key. Имя SQLite **не используется** — журнал относится к запущенному приложению, а не к загруженным в него данным.
2. Заголовок Runtime UI показывает `HTML: <filename> · версия: TEST_18_PR335`; выгрузка JSON содержит `htmlFile`, `archiveScope`, `archivePolicy`. Сборки TEST_17 не смешиваются с TEST_18.
3. Хранение ограничено **последними четырьмя сессиями каждого вида (Runtime и XLSX)** и **последними 384 событиями на сессию**. После записи элемента IDB удаляет выходящий за окно элемент с ключом `seq - 384`. Сессии сверх лимита удаляются при появлении новой, с их событиями. В UI кольцевой буфер ограничен 128.
4. Повторные `runtime-cache/progress` с `cacheHits` **не попадают в событийный WAL**. Их значения остаются в `aggregated.cacheHits`, а снимок счётчика сохраняется в localStorage на каждые 512 попаданий. События `runtime-sqlite-materialize`, ошибки и start/end тяжёлых фаз остаются полноценными событиями.
5. Скачиваемый TEST_18 JSON сериализуется без декоративных пробелов, чтобы уменьшить объём. Другие сборки получают прежний формат.
6. `diagnosticV2.globalSeq` относится к **сохранённым событиям**, а `cacheHits` — к подавленным повторам. Это осознанное разделение. `missingSequences` рассчитывается относительно допустимого окна 384 событий, а не всей накопленной за всю жизнь последовательности.

**Ограничение:** это ограничение **числа записей**, а не абсолютных байт файла; типовые небольшие события должны сохранять JSON существенно меньше прежних нескольких мегабайт. Невозможно гарантировать абсолютное ограничение в байтах без дополнительного байтового бюджета. Старый TEST_17 архив физически остаётся в профиле (в новый экспорт он не включается).

7. Проверки `test_diagnostic_scope_test18.js` и `test_diagnostic_archive_retention_test18.js` покрывают 55k повторов и удаление старых записей/сессий в эмуляции IndexedDB; реальная Opera ещё не проверена.

## 4. Следующие архитектурные шаги после компактной диагностики

**A. Непосредственно по TEST_17: найти и убрать 54k повторных `Runtime.get('itsm_data')`.** Определить конкретный вызывающий компонент (не гадать, что это KPI): ограниченно записать 3–5 анонимизированных call-site fingerprints и число обращений, затем переписать горячий цикл так, чтобы ссылка на Dataset получалась однажды на операцию, а не повторно на каждую строку. Дополнительно измерить CPU и время обработки до/после.

**B. Запретить неявную полную материализацию вслед за KPI SQL-проекцией.** В TEST_17 после облегчённой загрузки дополнительные потребители вызвали полные `get` для МБ и ITSM. Нужен контракт метаданных/страниц/SQL-проекций для конкретного экрана; поле `fullDataset.rows` допускается лишь при явном экспорте или просмотре небольшой страницы. Реальные места вызова устанавливаются тестом и call-site fingerprint, не по предположениям.

**C. Разгрузить KPI Worker.** Даже облегчённый путь передаёт сотни тысяч аналитических записей через structured clone. Следующий эксперимент: передавать агрегаты или ограниченные batch-проекции из SQL/Worker и сравнивать все KPI с эталоном TEST_17.

**D. Устранить постоянное удержание SQLite в WASM MEMFS.** На копии базы проверить отдельный DB Worker + OPFS/SAH pool, совместимость с целевой Opera и возможный локальный `file://` fallback. Не объединять этот высокий риск с диагностическим PR.

## 5. Условия приёмки

- При 55k попаданий в кэш: ноль новых WAL/IDB событий о попаданиях, счётчик `cacheHits=55000` сохранён.
- После перезагрузки того же HTML/профиля доступны его checkpoint и архив; другой HTML с другим именем получает независимые ключи.
- На каждом IDB store не больше 4 сессий × 384 событий одного `kind` (избыточные записи удаляются); события ошибки и тяжёлые checkpoints доступны после аварии, если хранилище успело подтвердить запись.
- Указаны честные `storageFailures`, `walPending`, `completenessKnown`. Очистки прежних архивов нет.
- В отчёте появились `htmlFile` и `archivePolicy`, а тестовые KPI и XLSX не изменились.
- Сравнивать **RSS Opera**, длительность операций и пиковую ёмкость WASM на *одинаковых* исходных данных, а не делать вывод по `mainJsHeapMiB`.
