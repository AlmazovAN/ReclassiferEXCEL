# V4-03 — контрольный корпус и протокол независимой инженерной проверки

**Задача:** воспроизводимая проверка будущего V4, не обучение на штатном Re-Class и не подгонка под инженерные четыре поля. Этот PR **не содержит алгоритм V4-04 и не меняет** `rules.js`, рабочий WebWorker, HTML, SQLite и Excel.

**Зависимость:** V4-02 (PR #289) ещё открыт и не принят; ветка V4-03 создана поверх `feature/v4-02-engine-registry`. PR V4-03 должен сравниваться с этой веткой, а не напрямую с `main`, пока V4-02 не принят.

## 1. Реестр и источник истинности

- `tests/fixtures/reclassification_v4_03_synthetic_corpus.json` — **17 исключительно вымышленных** случаев (12 development, 5 holdout; 2 стационарных). Они проверяют формат, распределение и предметные инварианты. **Это не результаты обработки реальной ITSM и не подтверждённый инженерный эталон.**
- `tests/reclassification_v4_03_validator.js` — проверка четырёх уровней ветки, обоснований, невозможности применить неподтверждённый результат, распределения дубликатов и утечек через общий текст.
- `tests/test_reclassification_v4_03_corpus.js` — положительная проверка реестра и отрицательные тесты нарушения его контрактов.
- `tools/reclassification/v4_03_private_manifest.js` — подготовка **локального черновика** из XLSX с сохранением под `local_data/` (эта директория уже исключена из Git). Работа только на машине пользователя, без публикации и сетевой загрузки.
- `tests/run_v4_03_codespaces.sh` — запуск в Codespaces с журналом и продолжением после ошибки.

**Корпоративные строки, реальные номера заявок, сотрудники и содержание диагностики не должны коммититься в Git.** Даже после обезличивания публикация реальных историй допускается только после соответствующего разрешения. Разработка может использовать синтетические минимальные примеры.

## 2. Поля одного кейса

| Поле | Назначение | Использование для вывода V4 |
|---|---|---|
| `id`, `incidentGroup`, `partition` | технический ID, общий физический инцидент, development/holdout | Только для организации тестов, не как признаки |
| `requestType` | оригинальный INC/RITM | Только исходный тип карточки |
| `population` | `mounted`/`stationary` | Контроль срезов |
| `source.shortDescription` | краткое описание заявителя | Да |
| `source.description` | исходное описание | Да |
| `source.closureNote` | примечания и фактический результат исполнителя | Да |
| `source.extraReason` | текст дополнительного поля причины | Да, как текст, не готовый ответ |
| `observations.reported / diagnosed / performed / outcome` | Отдельная фиксация жалобы, диагностики, действия и результата, заполненная рецензентом | **Нет; только контроль после вывода** |
| `reference.primaryPath` | штатные четыре поля ITSM | **Нет; только последующее сравнение** |
| `reference.engineerPath` | четыре поля инженерной разметки | **Нет; только последующее сравнение** |
| `reference.engineerOrigin` | `illustrative`, `unverified_engineering`, `verified_independent`, `none` | Не использовать как доказательство |
| `reference.engineerBranchStatus` | принадлежит ли полный путь справочнику: `in_classifier`, `outside_classifier`, `not_assessed`, `none` | Не использовать как предварительный ответ |
| `review.failureState` | `FAILURE`, `NON_FAILURE`, `UNKNOWN` | Только контроль |
| `review.disposition` | INC, RITM, скрытый отказ, неотказ, проверка | Только контроль |
| `review.proposedPath` | применяемая ветка 4 уровней или четыре `null` | Только контроль |
| `review.levelEvidence` | четыре отдельных основания | Только контроль |
| `review.status`, `reason`, `evidenceGrade` | источник заключения и достаточность | Только контроль |

`review.candidatePath` хранит частичный или спорный кандидат отдельно от применяемого результата. Для `READY` требуется действующая целая ветка и собственное основание по каждому уровню. Во всех иных случаях `proposedPath = [null,null,null,null]`, `applyReady=false`.

Синтетическая `classifier` — фиктивное демонстрационное множество веток, **не замена** действующего Failure Classifier из 6 586 комбинаций. Правильность на реальных данных проверяется только против версии справочника, указанной в акте выборки (контроль источника и SHA-256).

## 3. Протокол экспертизы реального обращения

Для каждой карточки инженер заполняет заключение по этапам.

1. **Что сообщил заявитель:** выделить дословное исходное описание и признаки жалобы. Не приравнивать жалобу к факту дефекта.
2. **Что установил исполнитель:** описать наблюдаемый отказ, диагностику, измерения, проверку отрицаний, исправный/неисправный объект; привести точную ссылку на фрагмент.
3. **Что делали и с каким результатом:** операции (замена, настройка, ремонт) отдельно от вывода о дефекте. Замена сама по себе не доказывает внутренний отказ, износ или причину.
4. **Что выбрал инженер:** отдельно сохранить `Наим1 / Элем1 / Неис1 / Прич1`, первоначально обозначить как **непроверенное**. Учитывать, что значения могли поступить из штатного Re-Class.
5. **Независимое заключение:** проверить факт отказа `FAILURE/NON_FAILURE/UNKNOWN`, аналитическую трактовку INC/RITM, каждый уровень, достаточность доказательств и существование ветки. Не смотреть готовый выбор алгоритма при первичном заключении.
6. **Верификация эталона:** `independently_verified` только после ручной проверки с указанием reviewerId/даты/версии справочника; разногласия фиксировать отдельной записью. `outside_classifier` — **не доказательство ошибки инженера**: возможны обновление/отсутствующая ветка/другая трактовка.
7. **Сравнение алгоритма:** только после фиксации экспертного вывода сравнивать каждый из четырёх уровней и весь путь; классифицировать расхождения: `V4_ERROR`, `REFERENCE_DISPUTED`, `SOURCE_INSUFFICIENT`, `CLASSIFIER_GAP`, `MULTI_DEFECT`. Не считать непросмотренные инженерные метки эталоном.

**Особый порядок для стационарного оборудования:** штатные J–M и производные метки не считаются экспертной разметкой. Каждый реальный стационарный кейс требует отдельного заключения по этапам 1–6, иначе `requires_independent_review` и не входит в метрики точности.

## 4. Методологические правила

| Ситуация | Предварительное ожидаемое решение |
|---|---|
| RITM, плановая работа без отказа | `KEEP_RITM`; четыре пустых поля, без Re-Class |
| RITM, диагностически доказан скрытый отказ | `RITM_AS_INC`; применяемая полная ветка только при доказанности |
| RITM, только жалоба, нет диагноза | `UNKNOWN/REVIEW`; без экспорта |
| INC, подтверждён отказ, причина не доказана | `PARTIAL/REVIEW`; не угадывать причину |
| INC, проверкой установлен неотказ | `INC_NON_FAILURE_OPEN`, без фиктивной неисправности и записи; **правило четырёх полей окончательно не согласовано до V4-12** |
| Несколько дефектов | раздельное рассмотрение, отсутствие произвольного единого ответа |
| Инженерный путь отсутствует в текущем справочнике | особый спорный кейс, не автоматическая ошибка инженера |

Не допускать circular evaluation: инженерные ответы и штатный Re-Class **не являются входными признаками V4**. В контрольном эксперименте менять инженерные метки и штатные записи при неизменных исходных текстах и справочнике: решение V4 должно оставаться прежним.

## 5. Срезы, отбор, разбиение

- Делить по **физическому событию** `incidentGroup`, а не по строкам. Дубли, связанные заявки, повторные эпизоды одного отказа не должны попадать одновременно в development и holdout.
- Делать первоначальный отбор по типам: обычный RITM, скрытый отказ RITM, INC с отказом, INC без отказа, неподтверждённый отказ, дубль, несколько дефектов, неверный объект, спорная/неустановленная причина, ветка отсутствует в справочнике.
- Отдельно отмечать установленность факта отказа, степень доказанности и происхождение маркировки. Выборка стационарного оборудования — только с независимой ручной проверкой.
- Не выбирать порог качества до проверки контрольного набора. Не включать в знаменатель точности неразмеченные и спорные случаи.
- Публичный синтетический `holdout` показывает механизм защиты от совпадения групп/текстов, но **не является закрытым слепым benchmark**: правильные ответы находятся в репозитории. Реальный контроль нужно хранить вне Git и вне файлов, читаемых реализацией правил.

## 6. Локальная подготовка частного реестра из Excel

После размещения выгрузки на **своей машине/в Codespaces** (если политика ИБ это допускает):

```bash
node tools/reclassification/v4_03_private_manifest.js --itsm "/private/path/ITSM.xlsx" --classifier "/private/path/FailureClassifier.xlsx"
```

Создаётся `local_data/reclassification_v4_03/private_manifest.json` с полями исходных данных, контрольными штатной/инженерной классификациями (НЕ эталон!) и метками `requires_independent_review`. `--force` перезаписывает прежний черновик. При отсутствии справочника статус `not_assessed`. Пожалуйста, **не пересылайте** этот JSON или вывод реальных текстов в GitHub issue/PR. Не размещайте закрытый файл в публичном контролируемом Git.

Автоматический split в частном черновике — лишь предварительный (детерминированный hash incidentGroup). Перед закрытием контрольной части необходимо вручную объединить связанные физические события с разными номерами заявок; затем пересчитать split и зафиксировать независимый акт. Импортёр не объявляет инженерные значения проверенными.

Реальные Excel отсутствуют в доступных файлах текущего задания, поэтому ни заполненный производственный эталон, ни сверка с реальными 6 586 ветками **не подтверждаются этим PR**.
