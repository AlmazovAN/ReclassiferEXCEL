# V4-06: тип события, факт отказа и диагностический отчёт

Уточнение V4-07: к правому блоку добавлены BI:BP — выбор оборудования и предметного объекта диагностики с доказательствами. Текущий отчёт содержит 68 колонок A:BP. Оценка события может уточняться по различию проверенных объектов; исходная оценка сохраняется. Подробности — [V4-07](v4-07-diagnostic-objects.md).

## Результат и границы этапа

Новый независимый модуль `event_v4.js` читает только исходный текст через V4-05 и зарегистрированный тип по префиксу номера. Возвращает факт отказа, аналитический тип, доказательства, ограничения и следующий шаг. Не выбирает оборудование, элемент, неисправность или причину. Полный движок `independent-4.0` остаётся недоступным для применения: `V4_NOT_IMPLEMENTED`.

По уточнению пользователя от 19.10.2026 пересмотрены и V4-05, и **видимые диагностические колонки после AH**. Сохранение старого отчёта на 75 колонок больше не является критерием. Текущий отчёт — 60 колонок, A:BH: прежние A:AH (34 колонки) и новый блок AI:BH (26 колонок). Отдельный файл Reclassification сохраняет контракт 10 колонок и решения неизменного алгоритма 3.3.0. Его контрольный Git blob по-прежнему `8918f6079b5d18ca78074e831d2555eea7faeda7`.

База этапа: V4-05, PR #292, `1bee4bbd96f9d9702699c6c2deb121b51fa2d22e`. V4-04 (#291) и V4-05 при проверке ещё открыты; новый PR направляется в ветку V4-05. Слияние в main до приёмки не выполняется.

## Решения V4-06

`ReclassifierEventAssessmentV4.analyze(row)` сам вызывает `ReclassifierTechnicalFactsV4.extract(row)`. Инженерные ответы, классификации ITSM, legacy-результат, MB-комментарии и runtime/SQLite не читаются. Дополнительные свойства не участвуют в решении. Результат глубоко заморожен, вход неизменен.

| Условия по исходному тексту | Факт отказа | Аналитический тип и действие |
|---|---|---|
| Явный установленный дефект или проверенная потеря функции в диагностике/закрытии | `FAILURE` | `INC`, в том числе для исходного RITM; продолжить техническую классификацию |
| Нет неразрешённых симптомов/гипотез; есть явная проверка без неисправностей | `NON_FAILURE` | Для RITM — `RITM`, цепочка пустая, исключить из реклассификации |
| Обычный RITM: описаны сервисный запрос и выполненные сервисные работы, отсутствуют сигналы отказа | `NON_FAILURE` | `RITM`, цепочка пустая, исключить из реклассификации |
| INC и доказанный по тексту неотказ | `NON_FAILURE` | `UNKNOWN`, ручной разбор; политика `INC_NON_FAILURE_V4_12` отложена до V4-12 |
| Есть одновременно диагностическое утверждение отказа и наблюдение неотказа | `CONFLICT` | `UNKNOWN`, ручной разбор без выбора последнего утверждения по порядку |
| Только симптомы, замена, восстановление, гипотеза, история либо недостаток данных | `UNKNOWN` | `UNKNOWN`, ручной разбор; тип по префиксу отдельно сохранён |

`sourceType` — `INC`, `RITM`, `UNKNOWN`; распознаются префиксы с цифрой, дефисом, пробелом или концом строки. Произвольный номер не считается INC по умолчанию. Номер определяет только зарегистрированный тип; технические выводы одинаковы при смене номера в пределах проверяемого текста.

`reviewRequired` относится к **разбору события на данном этапе**: при установленном отказе следующий шаг — продолжить классификацию, при обычном RITM — пропустить, при UNKNOWN/CONFLICT или отложенной политике — инженер. Это не готовность четырёхуровневого решения. Во всех случаях `candidatePath: [null,null,null,null]`, `readyForApply: false`, `independentlyVerified: false`, `evidenceBasis: source_text_only`.

«Подтверждён» означает наличие прямого диагностического утверждения **в исходном тексте**, а не независимый осмотр оборудования. Основания содержат точный исходный фрагмент, поле и UTF-16 позиции `[start,end)`. Числовая уверенность не выдумывается.

«Отказ не подтверждён» сам по себе оставляет UNKNOWN. «Неисправностей не обнаружено» не перекрывает необъяснённые симптомы из другого фрагмента. Исторические отказы не превращаются в текущие. Наличие замены и восстановления не доказывает отказ заменённого объекта. План и предположение не становятся подтверждением.

## Пересмотр V4-05

Версия извлечения повышена до `4.0.0-facts.2`. Понятные составные фразы, например «кабель заменён, связь восстановлена», разделяются с сохранением исходных позиций. Для условных, предположительных и планируемых фрагментов дополнительное разделение по запятой не выполняется: иначе «возможно»/«если» могло бы потерять область действия. У смешанного условного фрагмента сохраняется статус предположения даже при неопределённой роли.

Порядок внутри поля — расположение текста, а не доказанная хронология события. Порядок разных полей неизвестен. Даты выполнения/закрытия не используются для переупорядочивания диагностических утверждений. Наследование явно заданного заголовка раздела остаётся ограниченным одним исходным полем.

## Новый правый блок Excel

| Колонки | Содержание |
|---|---|
| AI | Версии технического разбора |
| AJ:AM | Симптомы, диагностика, действия, результаты |
| AN:AR | Отрицания, предположения, планы, неразобранные фрагменты, исходный тип |
| AS:AV | Аналитический тип, тип события, факт отказа, основание |
| AW:BB | Противоречия/ограничения, следующий шаг, необходимость разбора события инженером, исключение неотказа, отложенная политика INC, последовательность внутри полей |
| BC | Явный признак: V4 не готов к применению |
| BD:BH | Версия и решение алгоритма классификации 3.3, включение в Reclassification, его опора и комментарий МБ |

`diagnostics_v4.js` строит эти колонки из результата V4-06. Каждый фрагмент показывает исходное поле, позиции и статус. Отрицание/предположение может одновременно находиться в колонке своей технической роли: это разные характеристики, а не дубликат решения. Нераспознанные фрагменты остаются видны.

Старые видимые «этап отсечения», veto, счётчики уровней, кандидаты и способы выбора каждого уровня удалены из правого блока. Внутренний массив диагностик 3.3 пока остаётся промежуточным представлением штатного каскада и для чтения старых исходных полных выгрузок; он больше не определяет видимые правые колонки. Исторический golden-файл не переписан: проверяются его A:AH и 10-колоночный ReClass, а новая правая часть проверяется отдельно.

A:AH сохраняют заголовки и расчёты; группа O:T явно подписана «Reclassifier 3.3». AI и далее подписаны как независимый V4 без применения. Вывод V4 о факте отказа не меняет экспортируемые/применяемые legacy-решения. Сводка и пояснение в интерфейсе разграничивают эти результаты. Комментарии МБ доступны для просмотра, в распознавании не участвуют.

Ширина, фильтр и две закреплённые строки применяются к новому диапазону A:BH. Сохраняются группировки и подсветка первичной/инженерной/машинной классификации. Значения длиннее лимита Excel 32 767 символов сокращаются с явной пометкой; исходные поля остаются источником полного текста. Для V4 берутся исходное примечание и отдельная дополнительная причина; ранее добавленный идентичный суффикс объединения удаляется из примечания во избежание двойного разбора причины.

## Проверка и ограничения

```bash
git fetch origin
git switch feature/v4-06-event-diagnostics
git pull --ff-only origin feature/v4-06-event-diagnostics
bash tests/run_v4_06_codespaces.sh full
tail -n 100 ~/v4-06-codespaces.log
```

Запускать дочерним процессом, без `source` и без `set -e` в интерактивной оболочке. Скрипт продолжает проверки, считает PASS/FAIL и сохраняет единый журнал. По умолчанию код выхода 0 защищает терминал и сам по себе не подтверждает приёмку. Для автоматической проверки: `V4_06_STRICT=1 bash tests/run_v4_06_codespaces.sh full`. Журнал можно задать через `V4_06_LOG_PATH`. Тестовый процесс работает с TZ=UTC.

Проверяются факты, типы событий, скрытые отказы RITM, обычный сервис, отсутствие доказательств, противоречия, утечки контрольных ответов, неизменность входов, проекция диагностик, ограничения Excel, реальный XLSX, файл/Runtime, A:AH, неизменный 10-колоночный ReClass, V4-01–04, 5 000 строк, CORE-сборка и обе копии Browser/Worker.

Ограниченные русскоязычные эвристики не являются полноценным NLP. Различия объектов, причинная связь и реальная хронология относятся к следующим этапам. Противоречие может оказаться нормальной последовательностью «отказ → ремонт → исправно», но без надёжной связи по объекту/времени этот этап не угадывает её. Реальные инженерные Excel не предоставлены: производственная точность не установлена. Синтетические проверки и локальная сборка не выдаются за испытания пользователя в Codespaces.
