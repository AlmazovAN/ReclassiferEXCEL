# V4-07: реально отказавшее оборудование и объект диагностики

## Объём

`objects_v4.js` связывает диагностическое утверждение V4-06 с явно названным объектом и родительским оборудованием из активного индекса V4-04. Техническое прочтение остаётся независимым: исходная и инженерная классификации, выводы legacy, MB-комментарии и Runtime/SQLite не являются признаками.

База этапа — PR #293 (V4-06), `89ebfe05309e1ae172f417ade51742ef585fb5f7`. При проверке он открыт. Новый PR направляется в его ветку, без слияния зависимостей до приёмки.

В этом этапе выбирается **первый уровень оборудования** и сохраняется предметный объект диагностики. Совпавшее каноническое имя элемента — доказательный объект для следующих этапов, а не автоматически завершённая классификация второго уровня. `candidatePath` содержит только оборудование: `[selectedEquipment,null,null,null]`. Неисправность и причина не выбираются, `readyForApply: false` всегда. Полный движок independent-4.0 остаётся недоступным для применения.

## API и справочник

- `buildContext(index)` принимает неизменяемый индекс V4-04, компилирует названия оборудования и элементов и согласованные эквивалентные алиасы.
- `fromPreparedRecords(records,meta,options)` — адаптер существующего worker-контракта: подготовленные объекты `{equipment,element,failure,cause}` (историческое `fault` принимается как имя поля) или компактные массивы ровно из четырёх значений. Используется тот же V4-04 index, без параллельного справочника и без доступа к legacy context.
- `analyze(eventAssessment,context)` использует только результат технического извлечения/оценки события и словарный контекст. Возвращает глубоко замороженные роли объектов, кандидатов, выбранное оборудование, отказавший объект, ограничения, доказательства и происхождение справочника.

Контракт worker предусматривает **уже активный и отфильтрованный** Dataset. Адаптер не устанавливает активность сырых строк заново: массивы с дополнительными флагами, объекты с `disabled`/`sadu` отклоняются. Фильтровать реальные исходные Excel должен штатный Failure Classifier normalizer. Пропуск служебных фильтров не разрешён. Метаданные активного справочника передаются из UI в worker, а индекс сохраняет предусмотренные строковые поля происхождения. Если версии/отпечатка нет, `versionIdentified: false`; версия не выдумывается.

Учитываются лишь алиасы `approved` + `equivalent`, с канонической целью, областью и источником по контракту V4-04. `proposed` и `diagnostic` не становятся эквивалентами. По умолчанию алиасы отсутствуют; производственные сокращения без инженерного согласования не добавляются. Worker поддерживает явный реестр `classifierAliases`; интерфейс редактора и автоматическое наполнение словаря в этот этап не входят.

Для камеры, кабеля, блока, питания, коммутатора и датчика поддержаны ограниченные падежные формы. Это грамматические варианты того же слова, а не отождествление разных технических терминов. Остальные названия ищутся точно с нормализацией регистра/ё и пробелов. Проверяются границы слов: «блок» не совпадает с «микроблоком». Канонические названия в выводе сохраняются, коллизии не скрываются. Лексические неизвестные остаются в исходных фрагментах.

## Принципы связи

| Технический текст | Поведение |
|---|---|
| Нет изображения камеры; обнаружен обрыв кабеля камеры | Камера — объект симптома; кабель — диагностированный объект отказа |
| Заменён блок питания; связь восстановлена | Действие и результат не доказывают отказ блока |
| Выявлено отсутствие питания камеры | Установленная потеря функции не локализует неисправный аппаратный объект |
| Проверена камера: исправна; обнаружен обрыв кабеля камеры | Разные предметные объекты могут снять общее противоречие V4-06 |
| Кабель исправен; обнаружен обрыв того же кабеля | Противоречие сохраняется, хронология не достраивается |
| Один кабель встречается у нескольких видов оборудования | Все родители сохраняются; одних симптомов «СВР» недостаточно для выбора |
| Диагностический объект и «СВР» явно указаны в одном фрагменте | Родитель сужается только по совместимым веткам индекса |
| Несколько дефектов/объектов либо экземпляры №1 и №2 | Первичный объект не угадывается; ручной разбор |
| Одно сокращение имеет несколько согласованных значений | Неоднозначность видна, один вариант не выбирается по порядку |

Для поиска отказавшего объекта используются **только** фрагменты с поддерживающим диагностическим доказательством V4-06. Предположения, планы, отрицания, исторический контекст, действия и результаты сами по себе не задают отказавший объект. Объекты сохраняются отдельно по ролям `symptoms`, `diagnosis`, `actions`, `results`, `uncertain`.

Внутри диагностического фрагмента ищется ограниченная лексическая связь явного дефекта и ближайшего наименования, на расстоянии не более 60 символов. Связь не проводится через отрицания, сравнения, границы предложений и ограниченные предлоги/союзы. Координация нескольких объектов создаёт ограничение, а не право выбрать ближайший. «Камера» внутри более полного «Кабель камеры» не становится вторым отказавшим объектом. Явные идентификаторы `№1` и `-1` сохраняются; неописанные экземпляры не выдумываются.

Оборудование выбирается при одном согласованном диагностическом объекте, допустимой связи с родителем и отсутствии блокирующих ограничений. Основание указывается явно: оборудование в том же диагностическом фрагменте либо единственный родитель объекта в справочнике. Последний случай является **выводом через словарную связь**, а не прямой цитатой названия оборудования из текста. Если родитель отсутствует/неоднозначен или контекст несовместим, выбор не выполняется. Объект с симптомами сам по себе не сужает множество родителей диагностированного объекта.

Противоречие V4-06 уточняется до FAILURE лишь когда все противоположные наблюдения исправности имеют явно отличающиеся предметные объекты/экземпляры. Общая фраза «неисправностей не обнаружено», наблюдения о том же объекте или неясная область оставляют CONFLICT. Исходная оценка события сохраняется; отдельное поле показывает результат после разбора объектов. Ни порядок полей, ни завершение ремонта не используются как искусственная временная связь.

## Выход и диагностика

Статусы: `SELECTED`, `UNRESOLVED`, `NOT_APPLICABLE`, `MULTIPLE_OBJECTS`, `AMBIGUOUS_OBJECT`, `AMBIGUOUS_EQUIPMENT`, `CONFLICT`. Для невыбранного объекта `selectedEquipment` и `failedObject` пусты. При неотказе выбор не требуется. Разрешённое оборудование и канонический диагностический объект не означают готовность полной четырёхуровневой ветки.

Для каждого предметного совпадения сохраняются поле, исходное написание, UTF-16 смещения `[start,end)`, каноническое имя, режим распознавания и идентификатор экземпляра. Доказательства дополнительно сохраняют полный диагностический фрагмент и границы диагностического признака. Текст не нормализуется с потерей исходных позиций. Повторные упоминания одного неразличимого объекта не объявляются разными физическими объектами; разные явно названные родители и экземпляры не сливаются.

К существующему отчёту V4-06 добавлено восемь колонок **BI:BP**:

| Колонка | Содержание |
|---|---|
| BI | Оборудование по диагностике |
| BJ | Отказавший объект |
| BK | Статус выбора объекта |
| BL | Основание выбора объекта и словарные родители |
| BM | Объекты симптомов |
| BN | Проверенные/диагностированные объекты |
| BO | Ограничения выбора объекта |
| BP | Факт отказа после разбора объектов |

Итого **68 колонок A:BP**. A:AH и первые 26 диагностических колонок V4-06 сохраняют расположение; заголовок необходимости инженерного разбора расширен с события на совокупный разбор события и объекта. Аналитический тип и следующий шаг учитывают уточнённую оценку объектов. Сохраняются первая оценка факта отказа и отдельная уточнённая, чтобы результат был проверяемым.

Колонки O:T и отдельный Reclassification по-прежнему отражают действующие решения 3.3.0, а не автоматическое применение V4. Контрольный Git blob legacy `8918f6079b5d18ca78074e831d2555eea7faeda7` сохраняется. Комментарии МБ остаются только для просмотра. Сводка включает количества статусов выбора объекта. Длинные текстовые ячейки сокращаются с явной пометкой по прежнему лимиту Excel.

## Проверка

```bash
git fetch origin
git switch feature/v4-07-diagnostic-objects
git pull --ff-only origin feature/v4-07-diagnostic-objects
bash tests/run_v4_07_codespaces.sh full
tail -n 100 ~/v4-07-codespaces.log
```

Запускать дочерним процессом, не `source`. Код 0 по умолчанию защищает интерактивный терминал, но не подтверждает приёмку: смотреть итоговые PASS/FAIL. Для автоматики `V4_07_STRICT=1 bash tests/run_v4_07_codespaces.sh full`. Журнал задаётся `V4_07_LOG_PATH`. Проверяется весь предыдущий набор и новые проверки: роли, грамматика, алиасы/области, коллизии, неоднозначные родители, несколько объектов и экземпляров, отсутствие аппаратной локализации при потере функции, разбор противоположных наблюдений, точность исходных позиций, неизменность входов, реальный XLSX, 5 000 строк, Browser/Worker и legacy.

## Практические ограничения

Это ограниченный детерминированный разбор русскоязычных фраз, а не универсальный синтаксический анализатор. Не решаются местоименные ссылки между предложениями, произвольные технические сокращения и сложные вложенные связи. При неизвестных наименованиях, сложном перечислении и отсутствии явной связи сохраняется ручной разбор. Реальные инженерные Excel не предоставлены; качество на производственных обращениях не установлено. Числовая уверенность не вводится.

Следующий этап V4-08 — дальнейший выбор элемента по диагностическим доказательствам; конкретные границы следует сверить с полной дорожной картой на 14 PR, которой в текущих материалах нет.

Фактическая локальная проверка 19.10.2026: полный runner — **26 PASS / 0 FAIL**; дополнительный архитектурный тест — 4 теста, OK. Отдельно повторён интеграционный тест XLSX после добавления проверок файл/Runtime и независимости от комментариев МБ. Пользовательский Codespaces и реальные инженерные Excel не проверялись.
