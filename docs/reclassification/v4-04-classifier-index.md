# V4-04 — индекс разрешённых веток и семантика справочника

Задача: предоставить последующим этапам независимого V4 неизменяемый снимок разрешённых четырёхуровневых веток. Этот этап не распознаёт обращения, не выбирает классификацию по тексту и не делает V4 доступным для применения или экспорта.

База разработки: `main`, `dcfdb975ffeb360dcf1a487efd6c49e6e7eaf21d` (V4-03). Неприкосновенный `rules.js`: Git blob `8918f6079b5d18ca78074e831d2555eea7faeda7`.

## 2. Входной контракт и граница ответственности

`ReclassifierClassifierIndexV4.buildIndex(dataset, options)` получает штатный подготовленный объект `{records, validation, meta}`:

- `validation.status`: `valid` или `warning`; `invalid` и отсутствие статуса отвергаются.
- `records`: объекты с `service`, `equipment`, `element`, `failure`, `cause`. Это результат существующей фильтрации по услуге, деактивации и САДУ. Для Active Runtime вызывающая сторона передаёт актуальный подготовленный Dataset, например из `ReclassifierFailureClassifier.get()`; сам индекс глобальное состояние не читает.
- Сырые Excel, legacy-массивы путей и записи с полями сырых флагов не принимаются. Новый парсер и параллельная фильтрация не вводятся. API не может доказать происхождение произвольного объекта, вручную названного `valid`; ответственность за подготовку остаётся у штатного загрузчика.
- Неполные строки исключаются только из множества полных веток и остаются в диагностике с нулевыми индексами строк. Пустой подготовленный набор даёт пустой индекс, а не разрешение классифицировать.
- Fingerprint текущего пользовательского справочника используется только как метаданные происхождения; строки и исходники не сохраняются в репозитории.

Индекс не меняет исходные записи, Dataset Store, Active Runtime, SQLite или ITSM. Снимок не обновляется при последующих изменениях исходного объекта. После применения новой версии Dataset вызывающая сторона должна построить новый индекс; скрытого кеша нет.

## 3. Поиск и нормализация

Нормализация совпадает по смыслу со штатной нормализацией текстовых ключей: NBSP заменяется пробелом, пробелы схлопываются, края обрезаются, регистр приводится к русскому нижнему. Пунктуация и `е/ё` не объединяются. Точные канонические строки сохраняются без переписывания.

Ключ полного пути — JSON-массив четырёх отдельно нормализованных значений. Ветки берутся только из полных исходных записей. Декартово произведение значений не создаётся.

| Метод / свойство | Назначение |
|---|---|
| `list()` | Все уникальные полные канонические ветки `{id, path, sourceRow}`; id локален для снимка |
| `lookup(path)` | `EXACT`, `NORMALIZED`, `AMBIGUOUS`, `NOT_FOUND` либо `INCOMPLETE`; ветки и признак `collision` |
| `children(prefix)` | Реальные дочерние значения и соответствующие полные ветки; префикс длиной 0–3 |
| `byComponent(level, term)` | Обратный поиск веток, оборудования и элементов; только существующие сочетания |
| `resolveAlias(level, term, prefix)` | Разрешение согласованного эквивалентного алиаса в рамках области действия |
| `causeSemantics(path)` | Словарный тип четвёртого уровня, записи обоснований, конфликт и необходимость проверки |
| `causeReviewRegister()` | Реестр семантической проверки по существующим веткам |
| `provenance` | Снимок переданных метаданных происхождения и версии |
| `diagnostics` | Неполные строки, точные дубли, коллизии нормализации, upstream-статистика |

При точном каноническом совпадении допускается `EXACT` с `collision=true`: указанная ветка реально существует, но её нормализованный ключ неоднозначен. При поиске с изменённым написанием в таком случае возвращается `AMBIGUOUS` со всеми кандидатами; первый вариант не выбирается. `children` возвращает `ambiguousPrefix`, если нормализованный префикс объединяет разные канонические префиксы. Все результаты заморожены, внутренние Map наружу не передаются.

Штатный нормализатор уже удаляет некоторые дубли по пяти текстовым полям и сохраняет первый вариант. Утраченные до индекса варианты восстановить невозможно; это прямо отражено в `diagnostics.upstreamNormalizationLoss`. Коллизии, сохранившиеся во входном снимке, индекс не скрывает.

## 4. Управляемые алиасы

По умолчанию словарь алиасов пуст. Схема записи:

```js
{
  term: 'БП', level: 'element', canonical: 'Блок питания',
  scope: ['Станция'], kind: 'equivalent', status: 'approved',
  source: 'Идентификатор согласования и инженерного источника'
}
```

Пример исключительно иллюстрирует контракт, не утверждает производственное соответствие. Допустимы уровни `equipment`, `element`, `failure`, `cause`; `scope` — префикс предшествующих уровней. Каноническая цель должна существовать с точным написанием в переданном справочнике и области действия, иначе построение отклоняется.

`status`: `proposed` / `approved`; `kind`: `equivalent` / `diagnostic`. При поиске работают только `approved + equivalent`. Диагностическое выражение, предложенный синоним, симптом, результат ремонта или действие не становится эквивалентностью автоматически. Несколько разных канонических значений возвращают `AMBIGUOUS`, а не первое совпадение. Префикс запроса ограничивает результаты; кандидат всегда относится к реальной полной ветке.

Прямой `lookup` не подменяет термины алиасами. Словарное разрешение не доказывает факт отказа: `evidenceProven=false`. Номера заявок, ITSM-метки, инженерные ответы, прошлый Re-Class и эталонные тестовые ответы индекс не принимает как признаки решения.

## 5. Семантика четвёртого уровня

Поддержаны типы `factual_cause`, `explicit_unknown`, `action_or_circumstance`, `symptom_or_disputed`; без согласования — `unreviewed`. Реестр `options.causeSemantics` использует `{canonical, scope, kind, status, source}`; область действия — префикс длиной 0–3. Неизвестная цель отклоняется. Противоречащие утверждённые типы дают `CONFLICT` и обязательную проверку, даже если одно правило имеет более узкую область: молчаливого приоритета нет.

Встроены только **предложения для согласования** по девяти точным названиям, фактически найденным в baseline: «Причина не установлена (Акт, фото)», «Монтаж», «Демонтаж», «Настройка», «Тестирование оборудования», «Дублирование заявки», два написания «Отказ не подтверждён» и «Внутренний отказ (без признаков)». Это буквальный аудит названий, а не инженерная экспертиза причин; предложения имеют `status=proposed`, отображаются в `suggestedKinds`, не становятся `REVIEWED_LABEL` и не снимают необходимость проверки. В другой версии справочника предложения появляются только для реально существующих точных значений. Если передан собственный реестр, он заменяет набор предложений.

Даже утверждённый `factual_cause` означает только тип словарного значения. **Ни один ответ API не устанавливает причину конкретного обращения: `evidenceProven` всегда false.** Допустимость ветки с неизвестной причиной проверяется обычным `lookup`: она не добавляется в отсутствующие ветки и не превращается в доказанную фактическую причину. Применение такой ветки требует отдельно согласованной методики следующих этапов.

## 6. Сборка, регрессии и приёмка

Модуль включён до `rules_v4.js` в основной JS-bundle и в код WebWorker через `build/build.py`. Он не подключён к предметной обработке или экспорту. `rules_v4.js` продолжает завершаться `V4_NOT_IMPLEMENTED`; legacy 3.3.0, форматы ITSM 75 / Reclassification 10 и существующие действия применения сохраняются.

Приёмочный запуск в Codespaces, без `set -e` в интерактивной оболочке:

```bash
git fetch origin
git switch feature/v4-04-classifier-index
git pull --ff-only origin feature/v4-04-classifier-index
bash tests/run_v4_04_codespaces.sh full
tail -n 100 ~/v4-04-codespaces.log
```

Скрипт продолжает проверки после ошибок, пишет журнал и печатает точное число PASS/FAIL. По умолчанию `exit 0` защищает интерактивный терминал; **этот код выхода сам по себе не означает успешную приёмку**. Для автоматического runner: `V4_04_STRICT=1 bash tests/run_v4_04_codespaces.sh full`. Часовой пояс дочернего процесса закреплён в UTC: существующий тест Excel-дат сравнивает ISO UTC-день и в Asia/Dubai без этого давал сдвиг на день. Производственный код дат этим PR не меняется.

Quick: 14 проверок; full: ещё нагрузочный тест, реальная CORE-сборка, две проверки браузерного/worker bundle и smoke запуска (всего 19 при успешной сборке). Python-проверки здесь целевые, а не полный discovery всех тестов репозитория. Сборка использует штатную проверяемую загрузку SQLite WASM, если локального архива нет.

Критерии: каждая выдаваемая ветка есть в переданном наборе; несовместимые комбинации отвергаются; коллизии и неоднозначные алиасы не скрываются; источник и канонические названия сохранены; входы неизменны; V4 остаётся недоступен; пройдены V4-01/02/03, нормализатор, экспорт, сборка и smoke. Локальный прогон не выдаётся за отдельный запуск в пользовательском Codespaces или производственную экспертную приёмку.
