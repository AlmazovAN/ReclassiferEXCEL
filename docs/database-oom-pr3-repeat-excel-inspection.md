# PR 3/5 · повторная загрузка годовых Excel в Opera

## Что показал второй диагностический отчёт

После успешной подготовки первой выгрузки МБ (72 283 строки) следующая
выгрузка за 2025 год (22 589 517 байт, 70 808 строк) была распознана:
`initial-inspection/end, ready:1`, затем новая очередь остановилась между
`candidate-reinspect/start` и `recognizer-xlsx/end` на втором разборе
**того же файла**. Журнал записывал `mainJsHeapMiB:2222` против `1020`
при первом импорте. В очереди было **два** файла, поэтому подготовленный
кандидат из предыдущего импорта мог оставаться в оперативной памяти.

## Исправления в этом PR

- `database_intake_ui.js`: сохраняем provenance `inspectedFile` только
  если **реальный первичный распознаватель** успешно проверил File. Не
  сохраняем новую копию байтов или workbook.
- `database_integration.js`: при подготовке кандидата из **того же
  экземпляра immutable File**, с тем же `size`, `lastModified` и
  `ready`/Dataset, используем результат уже выполненной проверки.
  Вместо второго `File.arrayBuffer() + XLSX.read() +
  sheet_to_json(70k rows)` отправляем `candidate-inspection-reuse`
  в диагностический журнал. Для нового File, прямого вызова engine,
  нераспознанного файла или несовпадающих метаданных старый полный
  `inspectFile` сохраняется.
- `dataset_classifier.js`: классификатору достаточно первых **25
  непустых логических строк** листа. Для настоящих SheetJS worksheet
  с `!ref` читаем диапазоны **до 128 физических строк**. Сохраняем
  прежнюю нумерацию `rowIndex`, даже если между строками были пустоты.
  Старые/fake листы без `!ref` используют исходную схему чтения.

### Сохранённые контракты

- Первичная валидация XLSX **не отключена**: обязательные колонки,
  корректность записей, ключи, даты и предупреждения по-прежнему
  проверяются при добавлении каждого файла.
- `fingerprint` (SHA256) продолжает рассчитываться при подготовке
  кандидата; `previewDatasetChange` и проверка ревизии SQLite не меняются.
- Даты ITSM, связь с заявками, трудозатраты, Full Dataset, `-D1/-D2`,
  право пользователя на `Подтвердить` и отдельный экспорт XLSX сохранены.
- Нет очистки ранее подготовленного `pendingPlan`: это означало бы
  потерю готового кандидата без согласия пользователя.

## Проверка в Opera

1. Сначала загрузить исходный Excel за 2026 год и дождаться статуса
   `prepared` (не нажимая `Подтвердить`, если проверяется именно сценарий
   двух подготовленных кандидатов).
2. Затем загрузить вторую выгрузку за 2025 год, размер 22 589 517 байт.
3. Проверить в журнале: **после** `candidate-prepare/start` должен
   появиться `candidate-inspection-reuse/end`, а не второй
   `candidate-reinspect/start → recognizer-xlsx/start`.
4. Убедиться, что обе строки очереди сохранились, вторая стала
   `prepared`, а SQL-предпросмотр и число строк (70 808) корректны.
5. Ничего не подтверждать в основной БД до проверки количества,
   дублей и итогового эффекта.

### Оставшееся ограничение (важно)

Этот PR **не** решает главную проблему дальнейшего масштабирования:
каждый `item.pendingPlan` в текущем Workspace удерживает полные массивы
аналитических записей МБ и Full Dataset до применения/отмены.
Дополнительно `runtimeSqliteInstanceCache` может сохранять большие
Dataset, а KPI строит фоновые снимки. Поэтому два больших кандидата
**могут всё ещё исчерпать память позже** (на Worker → main thread или
`candidate-sqlite-preview`).

Если повторная загрузка всё ещё завершится OOM, дальнейшая реализация —
**PR 4/5: SQLite staging с пакетной записью/планами без больших массивов
в JS**. Не устранять проблему автоматической записью кандидата в
основной Dataset: подтверждение должно оставаться явным.
