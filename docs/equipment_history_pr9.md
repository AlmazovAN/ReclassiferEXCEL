# Equipment History — модель наблюдений (PR 9)

История ведётся **раздельно по пяти исходным Equipment Dataset**: `mounted`, `stationary`, `transport`, `transport_start_points`, `zabbix`. `Equipment_Combined` — производный справочник без отдельной собственной истории. История **не связана с Drivers** и не меняет используемый сейчас знаменатель КТГ.

## Ключи и охват

- Mounted / Stationary: устойчивый `id`, секция `unit`.
- Transport: `transport__id`, секция `unit`.
- StartPoints: составной `unit + name`, поскольку отдельного устойчивого Equipment ID в этом источнике нет. **Переименование или перемещение StartPoints нельзя достоверно связать с той же сущностью.**
- Zabbix: `zabbix__id`, секция `__partition_unit`, производная от связи `equipment → id` Mounted/Stationary. Неопределённые секции отвергаются логикой PR 8.

Наблюдение относится **только к подтверждённым полным секциям** заменённого источника. Вне обновлённых секций состав считается прежним, а не повторно подтверждённым.

## Две оси времени

- `sourceDate`: дата в имени/метаданных исходной выгрузки, если распознана. Может отсутствовать. Не подменяется датой обработки.
- `observedAt`: дата фактической записи наблюдения в приложение (ISO UTC).
- `eventDate`: устанавливается только для `decommissioned`, по явному `not_working_since`, если распознана его календарная дата. Для перемещения, появления, изменения и отсутствия действительная дата физического события неизвестна.
- `commissioning_date` сохраняется лишь как `commissioningDateUnverified` — значение источника без подтверждённой семантики. Оно **не используется для определения даты ввода в эксплуатацию**.
- `first_observed` — первый факт наличия ID в наблюдении приложения, **не монтаж/покупка/ввод в эксплуатацию**.

## События

| Код | Значение |
| --- | --- |
| `first_observed` | ID впервые обнаружен в данной исходной истории |
| `returned_to_observation` | ID снова появился после отсутствия в подтверждённой секции |
| `moved` | `unit` изменился у того же ID (дата фактического перемещения не известна) |
| `attributes_changed` | Изменились наблюдаемые реквизиты без изменения рудника и статуса |
| `missing_from_complete_scope` | ID отсутствует в новом полном снимке своей секции; **не означает списание** |
| `decommissioned` | Появилась явная `not_working_since`; окончательное выбытие, повторное включение и изменение даты запрещены без отдельного разрешённого процесса корректировки |

Снимки `inherited-baseline` обозначают прежний каталог, существовавший до внедрения истории. Если старую дату наблюдения подтвердить невозможно, `sourceDate=null`, `observedAt=null`. Это предотвращает «изобретение» исторических дат.

## Хранение и согласованность

История — поле `equipmentHistory` в метаданных *исходного* Dataset: `{schemaVersion:1, snapshots, events, lastKnown}`. В HTML сохраняется вместе с экземпляром Dataset Store при подтверждении; в SQLite — в `dataset_state.state_json` **внутри той же REPLACE-транзакции**, что и записи каталога. При неуспешном коммите изменения снимков и событий откатываются. Файлы HTML и SQLite не ведут двух параллельных авторитетных историй.

Снимки содержат компактное представление выбранных полей по ID для всех наблюдавшихся строк обновляемых секций. История *не является доказательством* достоверности физических сроков службы оборудования. Периодические количественные исторические показатели планируются отдельно в PR 10. При крупных объёмах и длительной эксплуатации объём JSON-истории нужно контролировать в PR 12.
