# RFC: Reclassifer — устранение OOM на уровне архитектуры и аварийная диагностика

Статус: **исследование, без изменения рабочих алгоритмов**.  
Исходная экспериментальная база: TEST_15_PR324 / PR #324.  
Дата: 29.10.2026.

## 1. Наблюдения, которые уже подтверждены

- Пользователь наблюдает падения вкладки Opera по нехватке памяти, иногда при потреблении порядка 2 ГиБ. Это внешнее пользовательское наблюдение, **не измерение из Runtime JSON**.
- В Runtime JSON TEST_15 (18:43 UTC) 14 сессий и 750 архивных событий: история между некоторыми перезапусками **сохранилась**. Отображаемый счётчик активной сессии начинается заново. Это не доказательство потери всего архива.
- В сессии 18:35:02–18:35:20 после `candidate-records/start` на XLSX 17 826 884 байта, 54 753 строки, `end` отсутствует; новая сессия в 18:36:14. Причина завершения браузера непосредственно **не зафиксирована**.
- В сессии 18:40:56 после `runtime-sqlite-materialize/start` для `mobile_brigade_data` в 18:41:13 отсутствует `end`; новая сессия 18:41:54. Перед этим полная материализация `itsm_data` заняла 16,033 с.
- Та же `candidate-records` при другом запуске завершилась за 66,298 с. Весь `candidate-prepare` — за 72,224 с.
- В коде `openDatabase()` читает SQLite в `ArrayBuffer` и вызывает `sqlite3_js_posix_create_file()` (копирование данных в VFS). В журнале входная база: **902 045 696 байт (860,26 MiB)**; `sqliteWasmCapacityMiB` ≈861,06 MiB. Это **capacity**, не RSS процесса.
- `runtimeSqliteInstance()` обращается к `repository.getDataset(id)`, который материализует JS records и Full Dataset, затем хранит instance в `runtimeSqliteInstanceCache`. KPI инициирует полный `get` для `itsm_data` (54 753) и `mobile_brigade_data` (271 496).
- Импорт `integrationPrepareItsm()` получает records и Full Dataset из Worker, создаёт post-UPSERT представление и KPI Source на главном потоке. `integrationClone()` использует `JSON.parse(JSON.stringify())` в ряде путей.
- Для XLSX распознавание `recognizerInspectFile()` использует `XLSX.read(..., dense:true)`, но `integrationWorkbook()` выполняет ещё один полный `XLSX.read()` без `dense:true` (не все датасеты проходят именно этот путь). SheetJS сам предупреждает о высоком потреблении RAM при загрузке всего XLSX.
- `performance.memory` в JSON почти константа 16–18 MiB / `distinctHeapSamples=1`: не использовать как показатель памяти процесса. У текущего `file://` режима `crossOriginIsolated=false`; `measureUserAgentSpecificMemory()` в нём недоступен.
- Отчёт XLSX TEST_15 содержит 42 строки и 38 колонок, успешная сериализация; он не подтверждает безопасность больших XLSX.

**Предварительная гипотеза:** пик памяти возникает из одновременного удержания SQLite в WASM-VFS, входного ArrayBuffer и нескольких JS/Worker представлений аналитических и Full Dataset. Достоверный вклад каждого компонента пока неизвестен. Наличие утечки `retained objects` также не доказано.

## 2. Международные практики / первичные источники

1. SQLite WASM: `sqlite3_js_posix_create_file()` **копирует** переданный буфер в виртуальный файл. https://sqlite.org/wasm/doc/tip/api-c-style.md
2. SQLite WASM: OPFS и `opfs-sahpool` поддерживают файловое хранение в Worker, отличающееся от MEMFS. Ограничения origin, Worker, concurrent handles должны проверяться на целевой Opera / file://. https://sqlite.org/wasm/doc/tip/persistence.md
3. SheetJS: обычное `read` / `write` загружает и записывает полные файлы в памяти; `dense` уменьшает накладные расходы, но не превращает парсер в потоковый. https://docs.sheetjs.com/docs/demos/bigdata/stream/
4. Chromium: RSS, JS heap, native и WASM необходимо профилировать разными инструментами. https://chromium.googlesource.com/chromium/src/+/main/docs/memory/tools.md
5. Chrome DevTools: Task Manager Memory Footprint; Heap Snapshot/Allocation Sampling; отдельная цель Worker. https://developer.chrome.com/docs/devtools/memory-problems/
6. IndexedDB: транзакция `strict` повышает устойчивость сохранения относительно `relaxed`, но это подсказка браузеру, а не безусловная гарантия. https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability

## 3. Целевая архитектура

```text
┌─────────────── UI / Presentation (no raw Dataset arrays) ───────────────┐
│    thin metadata, paginated views, cancellable tasks, export progress    │
└──────────────────────────────┬───────────────────────────────────────────┘
                               │ bounded requests / metadata only
┌──────────────────────────────▼───────────────────────────────────────────┐
│    Query / Job coordinator (backpressure + bounded memory budget)       │
└─────────────┬─────────────────────┬──────────────────────┬───────────────┘
              │                     │                      │
     Database Worker        XLSX Import Worker      XLSX Export Worker
     SQLite file-backed*    incremental or chunked  incremental ZIP writer
     SQL projection rows    records/batches         bounded pages
              │                     │                      │
              └─────────────────────┴──────────────────────┘
                        durable repository / metadata
                 + separate append-only diagnostics
* OPFS/SAH pool if verified; fallback Worker MEMFS only with explicit size cap.
```

Core invariant: **два больших полных Dataset не должны одновременно существовать в JS как долгоживущие объекты, если расчёту достаточно SQL-агрегата или проекции**. Не возвращать массивы на сотни тысяч записей в основной поток без явного пользовательского запроса.

## 4. Этапы разработки — по отдельным Draft PR

### Этап 0. RFC и заморозка экспериментальных правок

- TEST_15 оставить отдельным Draft, не переносить в `main`.
- Сохранить два текущих диагностических JSON и их сравнение с TEST_13/14.
- Никаких новых оптимизаций до получения достоверного baseline памяти.

**Готовность:** опубликованы зафиксированные факты и гипотезы, определены контрольные сценарии.

### Этап 1. Диагностика V2 — только наблюдаемость

Отдельный PR с самостоятельным модулем телеметрии, не добавлять код в уже почти 30-КБ `database_ui_state.js`.

**Контракт событий:**
- `bootId`, `sessionId`, глобальная монотонная `seq`, `operationId`, `parentOperationId`;
- типы `start` / `checkpoint` / `end` / `error` / `recovered-interrupted`;
- `activeStep` + `lastDurablyAcknowledgedSeq` (не путать с попыткой записи);
- `bytesInputFile`, `sqliteVfsBytes`, `wasmCapacityBytes`, `activeInputBufferBytes` (по известным явным буферам);
- `runtimeCacheDatasets`, `runtimeCacheRecordCount`, `runtimeCacheFullRows` (именно счётчики, **не** численная оценка RAM);
- `workerGeneration`, `workerCurrentTask`, `messagesPending`, `transferBytes`, `batchRows`, `batchBytes`;
- `sourceFileByteLength`, `parsedWorksheetRows`, `normalizedRows`, `fullDatasetRows`, `candidateRows`;
- `jsHeapSampleBytes` только с явным `reliability: estimated/unavailable`, не подменять им RSS;
- признаков пользовательских данных, имён файлов, текстов заявок и строк XLSX **не включать**.

**Надёжность:**
- логирование каждой критической границы производится **до** тяжёлого синхронного вызова, после него и на доступных внутренних checkpoint;
- одна запись = один небольшой WAL checkpoint; асинхронная IndexedDB запись с контролем `commit` и возможным durability `strict` при поддержке;
- отдельный **постоянный архивный счётчик** и текущая сессия в интерфейсе: «всего / текущая / потеряно или не подтверждено»;
- по повторному запуску незавершённая старая сессия помечается `interrupted` только новым восстановительным событием, оригинальный архив не переписывается;
- детектор пропусков последовательности (gap), неуспешных `localStorage` и IndexedDB;
- вынести формат и место сохранения логов из UI-модуля; не JSON.stringify весь 360-event ring-buffer при каждом маленьком событии;
- нагрузочное тестирование журнала отдельно: 10k событий, quota denial, повторное открытие, искусственное завершение renderer/Worker;
- уведомление о невозможности надёжной записи **до** запуска большого задания.

**Результат:** при аварии Runtime JSON содержит старые сессии и последний подтверждённый checkpoint, а интерфейс не выдаёт сброс текущего счётчика за потерю истории. Для полного внешнего учёта RAM нужен Chrome/Opera Task Manager / OS монитор либо отдельный companion process.

### Этап 2. Реальный профиль памяти и разложение на компоненты

В Opera выполнить одинаковые сценарии на неизменной копии БД:
1. открыть HTML без БД;
2. открыть БД 860 MiB без KPI;
3. запросить небольшой SQL SELECT, без полной материализации;
4. запустить KPI и материализацию;
5. импортировать Excel 18 MiB до `candidate-records`;
6. завершить подготовку и COMMIT;
7. повторить без перезагрузки;
8. экспорт 12k×38 ячеек; контроль закрытия Worker;
9. повторить после восстановления вкладки.

В каждой контрольной точке: OS/browser **Memory Footprint/RSS**, JS heap, WASM capacity, cache record counts, активные Worker, старые удерживаемые объекты (DevTools Heap Snapshot). Различать **peak**, **after GC**, **retained** и **resident**.

**Результат:** отчёт атрибуции с объяснением прироста; без такого отчёта не менять API хранения.

### Этап 3. SQLite вне главного потока и файловое хранилище

- Прототип **Worker + OPFS/SAH pool** в отдельной экспериментальной сборке, тестирование возможностей реальной Opera и `file://`.
- При несовместимом `file://` сохранить полностью офлайн-работу через локальный `http://localhost` (не обращение в интернет) только как **дополнительный вариант**; single-file режим — отдельный fallback.
- Избежать полного VFS-дублирования там, где возможно. Перенести SQL-селекты в DB Worker; на UI возвращать только партии, метаданные и агрегаты.
- Восстановление БД после аварии, формат обмена, импорт/экспорт и контрольные суммы без потери существующих данных.

**Результат:** измеримое снижение пика и соответствие схемы SQLite на той же базе.

### Этап 4. KPI: SQL-проекции и агрегаты вместо полной материализации

- Составить таблицу полей, реально потребляемых каждым KPI.
- Считать фильтры/периоды по SQL там, где корректно и воспроизводимо.
- В Worker передавать минимальную проекцию / агрегаты / партии, а не полные `records` и `fullDataset.rows`.
- Проверить эталонное **побитовое/числовое соответствие** KPI TEST_14 и новой реализации (фиксированные источники, даты, разрезы).

**Результат:** KPI не требует передачи 271 496 Full Dataset строк и десятков колонок, если они не используются.

### Этап 5. Импорт/экспорт Excel без двойных полных деревьев

- Устранить повторный full parse: инспекция заголовков/семпла и одна финальная подготовка;
- `candidate-records` разбить на bounded batches и выдавать checkpoint по партиям;
- запретить `JSON.parse(JSON.stringify())` больших датасетов без явной необходимости;
- для экспорта — writer с ограничением памяти и записью ZIP/XLSX частями, а не накоплением целой книги;
- одна и та же схема/записи/Full Dataset, эквивалентность результата обязательна.

**Результат:** память относительно размера партии, а не размера всей книги.

## 5. Условия принятия и запреты

- Не изменять формулы KPI и исходные данные как часть «диагностического» PR.
- Не удалять SQLite, не обнулять IndexedDB/WAL и не очищать пользовательский профиль.
- Не выдавать `sqliteWasmCapacityMiB` или `performance.memory` за измерение RSS.
- Никаких заявлений «OOM устранён» без отчёта RSS/пика на воспроизводимом сценарии.
- Применять архитектурные ограничения, регрессионные тесты и полную проверку Codespaces для каждого отдельного PR.
- После TEST_15 **первым исполняемым PR делать диагностику V2**, а не очередное управление очередями задач.

## 6. Первое решение для следующего PR

Передачу в разработку считать согласованной по направлению: **диагностика V2 + baseline**, не рефакторинг SQLite / KPI / XLSX одновременно. После её прохождения принять решение по OPFS/Worker на основе измеренного профиля.

Это RFC, не утверждение, что конкретная архитектура OPFS уже проверена на фактическом `file://` в Opera.
