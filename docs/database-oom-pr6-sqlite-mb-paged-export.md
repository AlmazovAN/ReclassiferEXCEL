# PR 6 — Мобильные бригады: период и безопасный экспорт XLSX из SQLite

## Пользовательский сценарий

Подключённая `Reclassifier.db` выросла до ~826,74 МБ. Две большие
выгрузки МБ импортированы через последовательные сессии Opera. При
повторной обработке больших Excel без закрытия вкладки возможен OOM.
На странице «Мобильные бригады» вместо диапазона фактических дат
отображалась лишь кнопка «Выбрать период и скачать Excel».

В старой реализации:
- `mobileBrigadeDataMarkup()` вызывал
  `datasetStore.get('mobile_brigade_data')`;
- кнопка «Выбрать период...» меняла `mobileShowSqliteExport=true`
  и вызывала `ReclassifierRuntimeDataRepository.get('mobile_brigade_data')`;
- прежний универсальный экспорт также обращался к `datasetStore.get` и
  формировал весь Full Dataset в JavaScript;
- блок связанных справочников вызывал
  `moduleStatus.referenceRows(['itsm_data'])`, что могло
  материализовать полный ITSM Dataset.

При SQLite размером 826 МБ в браузере недостаточно просто иметь свободное
место на диске: `openDatabase` читает файл в `ArrayBuffer` и загружает его
во внутренний SQLite VFS/WASM. Многочисленные `getDataset` превращают
те же записи в дополнительные JavaScript-объекты и массивы.
`mainJsHeapMiB` НЕ измеряет весь WASM/Worker/браузерный процесс.

## Изменения

1. **Реальный период:** новый read-only API
   `getMobileBrigadeExportInfo()` читает только
   `json_extract(record_json, '$.factDate')` из SQLite и определяет
   минимальную/максимальную **фактическую дату работ**, число записей
   с датами и без них. Он не использует имена файлов, так что даты
   могут оказаться шире периода 2025–2026 гг.
   Применяется ровно тот же преобразователь календарного дня, что в
   legacy HTML Excel Export.
2. **Страница МБ:** сводная карточка теперь показывает количество строк
   и фактический период сразу, без `RuntimeDataRepository.get`.
   Связанный ITSM показывается по `dataset_registry.record_count`.
3. **Ручной XLSX:** `getMobileBrigadeExportPage(from,to,offset,limit)`
   читает SQLite курсором (JOIN аналитических дат с
   `dataset_full_records` по `record_key`), отбирает записи заданных
   дат и возвращает не более **10 000 полных исходных строк** за раз.
   Передача Worker и генерация XLSX только по прямому нажатию.
   Следующая кнопка «Скачать XLSX · часть N» скачивает следующую часть
   того же периода. Уникальные имена:
   `Mobile_Brigade_YYYY-MM-DD_YYYY-MM-DD_part01.xlsx`,
   `..._part02.xlsx` и т.д.
4. SQLite **read-only**; экспорт не подтверждает COMMIT, не изменяет
   records/state или исходный `.db`. Сохранены исходные колонки
   Full Dataset (никакой незаметной подмены аналитическими полями).
5. Если исходных колонок Full Dataset нет, полный экспорт
   недоступен с явным сообщением; скрытого экспорта неполных данных нет.

### Ограничение

Для устойчивости **одно XLSX содержит максимум 10 000 строк**.
Если выбранный период больше — сохраняйте части последовательно.
Для 190 тыс. строк это ~20 файлов, причём каждый формируется отдельно
и не удерживает все 190 тыс. записей в JavaScript. Opera может запросить
разрешение на многократное скачивание из локального HTML.

Это не является полным streaming XLSX writer или ZIP-мультиэкспортом.
При необходимости одного огромного XLSX потребуется отдельная реализация
потокового writer с ограничением памяти. Существующий Worker SheetJS
сам держит формируемую таблицу в памяти.

## Ручная проверка

1. Открыть `*_CORE_TEST_06_PR322.html`; подключить **копию**
   актуальной SQLite ~826 МБ.
2. Перейти сразу в «Мобильные бригады». В карточке «Данные в текущей
   базе» должны быть фактические даты МБ и количество строк. В
   боковой карточке — выбор дат и «Скачать XLSX · часть 1».
3. Проверить, что сама навигация не вызывает массовые маркеры
   `runtime-sqlite-materialize` только из-за карточек МБ/ITSM.
4. Выбрать небольшой период до 10 000 строк, скачать `part01.xlsx`;
   проверить все исходные колонки, количество строк, формат дат.
5. Для периода более 10 000 строк скачать `part01.xlsx`, затем
   `part02.xlsx`. Убедиться, что строки не повторяются и не теряются,
   а файлы корректно читаются Excel.
6. Проверить, что SQLite осталась неизменной и сохранение БД не
   требовалось.

Не загружать корпоративную SQLite в GitHub. При сбое отправить только
этап, текст ошибки и обезличенную диагностику.

## Дополнение: аналитические строки без Full Dataset (приёмка TEST_07)

В Opera база показала **271 496** записей за фактический период
**29.08.2019–25.09.2026** и **38** колонок Full Dataset. Прежняя
кнопка XLSX остановилась с ошибкой
`Отсутствует исходная строка Full Dataset МБ`.

Причина в модели хранения: `dataset_records` и
`dataset_full_records` — разные таблицы, и ранее в базе могли
храниться аналитические записи без полной исходной строки. Присутствие
заголовков 38 полей в `dataset_state.fullDataset` **не означает**
полного покрытия строк. Ошибка сама по себе не доказывает порчу БД;
фактическое количество строк без источника вычисляется из SQLite.

### Исправление (в этой же ветке PR #322)

1. `getMobileBrigadeExportInfo` дополнительно возвращает
   `fullRows` и `missingFullRows` с дешёвым SQLite LEFT JOIN по
   `record_key`, без передачи 38-колоночных JSON в память браузера.
2. На странице МБ показано, сколько строк имеют полный источник и
   сколько имеют **только аналитику**.
3. Явный выбор **режима экспорта**:
   - `Все записи — аналитические поля` — все датированные записи,
     фиксированный контракт аналитических полей (23 поля), нет потери
     записей из-за отсутствия Full Dataset; исходные поля, не
     сохранённые в аналитике, **не создаются и не угадываются**.
   - `Только сохранённые исходные строки Full Dataset` —
     реальные исходные 38 колонок **только для записей с
     сохранённым полным источником**; строки без него
     исключаются **явно и с предупреждением**.
4. При наличии сохранённого Full Dataset по умолчанию выбран режим
   **38 обработанных колонок**, как основной запрос пользователя.
   Отсутствующие строки в этом режиме исключаются с предупреждением;
   аналитический экспорт остаётся отдельным явным выбором.
5. Файлы различаются по режимам:
   `Mobile_Brigade_analytical_<from>_<to>_part01.xlsx` и
   `Mobile_Brigade_full_<from>_<to>_part01.xlsx`.
6. `getMobileBrigadeExportPage` запрашивает большой
   `f.row_json` **только для выбранных в выгрузку 10 000 строк**.
   При переходе к последующим частям большие JSON-строки не
   загружаются для пропускаемых записей.

Тест `tests/test_sqlite_mobile_brigade_paged_export.js`
дополнен искусственным пропуском Full Dataset: аналитический режим
сохраняет все 10 002 датированные строки в двух XLSX, режим
Full Dataset — только 10 001 действительно сохранённую исходную строку
в двух частях. Метаданные подтверждают 1 отсутствующую исходную
строку, не меняя БД. Изолированные динамические JS проверки — PASS.

## Дополнение TEST_09: длинный текст Excel и выбор 38 колонок

Пользователь подтвердил: 271 496 аналитических строк, **114 682 без
Full Dataset**, сохранены **156 814** полных 38-колоночных записей.
При экспорте периода, затрагивающего февраль–март 2025, был отказ
`Text length must not exceed 32767 characters`. Выгрузка апреля прошла.
Следовательно, источник сбоя — ограничение длины значения отдельной
ячейки Excel; конкретный проблемный столбец журналом пока не установлен.

В `src/js/workers/dataset_export_processor.js` добавлена безопасная
обработка текстов длиннее 32 767 UTF-16 кодовых единиц:

- На основном листе остаётся **первый фрагмент текста** и полный набор
  исходных колонок.
- На листе **«Продолжения текстов»** каждый последующий фрагмент
  содержит номер строки исходного листа, номер и название колонки,
  номер фрагмента (начиная со второго) и сам фрагмент. Восстановление:
  сцепить ячейку основного листа и все последующие фрагменты в порядке
  их номеров. Никакой символ не удаляется; пары UTF-16 суррогатов
  не разрезаются, чтобы сохранить Unicode.
- Нормальные короткие поля остаются как были; дополнительный лист не
  создаётся, если длинных текстов нет.
- Обработчик возвращает `longTextCells` и `overflowParts`, интерфейс
  сообщает пользователю, когда XLSX содержит дополнительный лист.
- Само ограничение Excel обойти нельзя. **На основном листе длинная
  ячейка отображается не целиком**, её полный текст восстанавливается
  с дополнительного листа. Изменений SQLite нет.

**38 колонок Full Dataset** — это выход обработчика МБ
(`ReclassifierMobileBrigadeRules.outputColumns`), а не побайтовая
копия всех входных полей оригинального Excel. **23 колонки** —
промежуточная аналитическая структура, непригодная как замена полной
обработанной выгрузки. По умолчанию экспортируются 38 колонок, если
в SQLite присутствуют сохранённые Full Dataset строки.

114 682 недостающие Full Dataset строки невозможно восстановить одним
экспортом. Для этого нужны первичные Excel и отдельный безопасный
контролируемый backfill по стабильным `recordKey`; нельзя подставлять
придуманные поля или выдавать аналитический XLSX за исходную выгрузку.

## Изменение по пользовательской приёмке — один XLSX без частей (TEST_10_PR322)

После успешного импорта и проверки экспорта пользователь попросил
**один скачиваемый XLSX за выбранный период**, без верхнего лимита
10 000 строк на пользовательский файл и без `part01/part02`.
Это нужно для самостоятельной работы в Excel (сводные таблицы, анализ).

### Реализация

- Интерфейс: одна кнопка **«Скачать XLSX»**, одно скачивание
  `Mobile_Brigade_full_YYYY-MM-DD_YYYY-MM-DD.xlsx` или аналогичного
  `analytical`. Период и режим сохраняются.
- Внутри SQLite чтение **по 10 000 записей**, но без ограничения
  количества таких партий: новый `EXPORT_DATASET_XLSX_STREAM` запрос
  WebWorker получает следующую партию только после обработки предыдущей.
- `WORKER_EXPORT_NEED_BATCH` / `WORKER_EXPORT_BATCH`: обратная связь
  Worker↔Main, с ошибками, проверкой монотонного смещения, ревизии БД
  и соответствия колонок. Пакеты не суммируются в массиве главного потока.
- Worker добавляет партии на один `dense` SheetJS worksheet, и только
  после завершения всех партий **один раз** вызывает `XLSX.write()`.
  Итог — **один XLSX**, а не множество файлов; сохранены 38 колонок
  для имеющихся исходных строк, даты, автофильтр и лист
  «Продолжения текстов» при больших комментариях.
- После завершения Worker может быть уничтожен для освобождения heap.
  Метка: `xlsx-worker-recycled/end`.
- Жёсткий технический предел Excel: **1 048 576 строк на лист,
  в том числе строка заголовков**. Запрошенные 271 496 записей в него
  укладываются. Однако в существующей БД Full Dataset сохранён
  лишь для **156 814**, поэтому режим `full` не выгрузит все 271 496:
  114 682 пропущенных строк нужно восстанавливать отдельно из исходных
  Excel (текущая выгрузка их не выдумывает).
- Память: XLSX Writer пока создаёт целый итоговый worksheet в памяти
  Worker и сериализует его. **Нельзя гарантировать, что Opera не
  упрётся в RAM/OOM на полном периоде.** В отличие от прежней версии,
  основной поток не держит сразу всю таблицу. Для действительно
  постоянной памяти Worker понадобится самостоятельный потоковый
  XML/ZIP writer, а не SheetJS `write()`.
