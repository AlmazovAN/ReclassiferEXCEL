# PR 4 — Фоновая очередь вычислений KPI и автономный Worker

## Назначение

Создаётся **отдельный KPI WebWorker** (в дополнение к существующему Worker для XLSX/ITSM/МБ) и управляемая очередь для запросов Calculator. Формулы и Calculator остаются неизменными; WebWorker загружает те же исходные JS-модули из единой HTML-сборки.

PR4 создаёт **действующий асинхронный расчётный API**:
`ReclassifierKpiBackgroundJobs.runQuery({sourcePack,signature,query,kpis,priority,key,signal,onProgress})`, а также `ReclassifierReliabilityReportService.calculateKpiAsync(query, options)`.

**Граница PR4:** существующие вызовы `buildSnapshot` / `buildKpiChartMultiData` остаются синхронными. Пользовательские страницы будут переводиться на асинхронную загрузку в PR5. PR4 сам по себе **не гарантирует ускорения** текущего отчёта.

## Механизм

- Первый запрос по явному действию создаёт dedicated Worker из Blob, упакованного в `window.RECLASSIFIER_ASSETS.kpiWorker` — никаких сетевых запросов или сторонних библиотек.
- `KPI_INIT`: передаётся sourcePack, вычисляются и остаются в памяти Worker предметные компоненты. Одна передача на одну ревизию + неизменность объектов Dataset.
- `KPI_CALCULATE`: передаются только запрос, ID показателей, идентификатор сессии и опциональное требование аудиторской трассировки. Используются уже подготовленные компоненты. Без повторной передачи входных записей.
- История в Worker хранится не постоянно: инвалидация сбрасывает данные при изменении Dataset. Восстановление после смерти Worker инициирует повторную загрузку только по новому запросу.
- `ReclassifierKpiTaskScheduler`: одновременно только одна работа; 64 ожидающие; приоритеты P0–P5; FIFO внутри одного приоритета; dedup по явному ключу; ограничение очереди; `AbortSignal`, invalidate, dispose и события прогресса.
- Если Worker уже исполняет длинную синхронную формулу, её нельзя прервать на середине: результат отменяется, следующая задача стартует **после завершения текущего шага**. Это ограничение отражено в API; «мгновенное прерывание» не обещается.
- Отсутствие Worker, ошибки передачи DataClone и авария Worker приводят к явной ошибке; приложение продолжает использовать существующий синхронный Report Service (не скрытая подмена методики).

## Память и безопасность

Исходный набор содержит сотни тысяч записей и его полное клонирование в Worker может увеличить потребление памяти. Поэтому **в PR4 передача Dataset не автоматизирована**, не выполняется при открытии приложения, отчёта или подключении SQLite. Реальные массовые KPI-задания следует подключать только после определения компактной входной проекции/агрегатов и замеров объёма в PR5–6.

Сетевые обращения не используются. Журнал показывает только статус/число заданий, не значения фильтров, фамилии или строки Dataset. В Worker нет SQLite и доступа к DOM.

## Совместимость и тесты

- `tests/test_kpi_task_scheduler.js`: приоритет, FIFO, объединение запросов, заполнение очереди, отмена, инвалидация, возобновление.
- `tests/test_kpi_worker_protocol.js`: готовность Worker, подготовка, формула, trace, запрет устаревших сессий.
- `tests/test_step9_browser_offline.js`: реально запускает отдельный Worker в `file://`, выполняет VBR на минимальном тестовом наборе, проверяет одинаковые результаты двух вызовов и повторное использование сессии; остальной тестовый набор для SQLite остаётся неизменённым.
- Полный CI, контроль действующих KPI и PDF, HTML сборка и работа без сети.
