# PR5 — постоянный кэш KPI в SQLite (DB Schema 5)

## Цель
Сократить повторный расчёт отчёта после открытия существующей Reclassifier.db.
Сохранённые результаты — необязательные производные данные, **не источник фактов**.

## Контракт хранилища
- **Миграция 4 → 5:** транзакционно создаётся `kpi_snapshots`, повышаются `PRAGMA user_version` и `app_metadata.schema_version`, записывается `schema_migrations`. Ранее созданные базы v1–v4 мигрируются существующей цепочкой. Данные `dataset_registry`, `dataset_records`, `dataset_state`, `dataset_full_records`, `import_history` сохраняются.
- **Идентичность:** `database_uuid`, фильтры `period/mine/equipmentClass`, проверяемая `source_signature`, действующие `dataset_registry.active_revision/content_hash/updated_at`, версия методики (версионный маркер + Catalog/Calculator/View/Forecast/Source Facts) и версия Report Snapshot.
- **Только полные Report Snapshot** (stage=full). Частичный/ошибочный/пустой результат, результат другой ревизии, другой методики или повреждённая запись не принимаются.
- **Хранение:** максимум 12 комбинаций фильтров/ревизий. Отдельная запись ограничена 8 млн UTF-16 кодовых единиц до JSON-сериализации. В таблице есть JSON CHECK, контрольная сумма и дата расчёта; при отказе чтения кэша выполняется обычный расчёт в Worker.
- **Операции:** `getKpiSnapshot` — только чтение, `putKpiSnapshot` — один SQLite COMMIT с записью и вытеснением старых строк. Исходные Dataset и их ревизии не изменяются. Повторная запись идентичного результата — no-op.
- **Сохранение:** новый снимок считается настоящим изменением рабочей SQLite, поэтому `dirty=true`. Это **не означает**, что изменения записаны в исходный системный файл: прежняя побайтовая проверка `saveDatabaseToFile` остаётся обязательной. Запрос на скачивание копии не подтверждает сохранение.
- **Нет отдельной очереди:** используются существующий Report Service и KPI Worker; полный снимок из актуального кэша возвращается до отправки большого набора исходных строк в Worker. После успешного нового расчёта снимок проверяется и предлагается репозиторию для записи.
- **Изоляция ошибок:** повреждение или недоступность необязательного KPI-кэша не должно блокировать чтение исправной основной базы. Кэш может быть пересоздан следующими успешными вычислениями.

## Принцип границы релизов
Маркер `KPI_SNAPSHOT_METHOD_REVISION` в Report Service нужно повышать при изменении семантики формул, состава расчётов или правил построения Snapshot. Строка версии приложения сама по себе не подменяет этот маркер. 

## Регрессионная приёмка
`test_sqlite_kpi_snapshot_pr5.js`: настоящая SQLite/WASM, создание и миграция v4→v5, независимость исходных строк, повторное открытие, размер/вытеснение, отклонение неверных ревизий, повреждённый кэш. `test_reliability_report_service.js`: путь Report Service → Repository → повторное чтение → отклонение изменённых источников. Полная CORE/FULL/SQLite/offline Chromium матрица остаётся обязательной.

## Ограничение
На пользовательской реальной SQLite большого объёма отдельная приёмка не проводилась: CI использует синтетические наборы. Сохранённая SQLite v5 может требовать текущую или более новую версию приложения для открытия.
