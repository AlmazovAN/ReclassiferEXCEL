# PR-8 — экспериментальная оценка задержанной реклассификации

## Назначение

Показатели `classification_quality` и `classification_quality_cgps` вычисляются по текущей категории качества A/B/C/D в ITSM. Фактический KPI остаётся:

```text
Качество классификации, % =
  classificationSuccessCount / classificationTotalCount × 100
```

Основные даты учёта — `completedAt`, при отсутствии — `closedAt`. Эти даты **не являются** временем последующего исправления инженером классификации. Текущая выгрузка содержит итоговые значения и не гарантирует исторические состояния по датам. Лог загрузок Dataset хранит метаданные о загрузках, но не содержимое всех версий обращения и не является журналом изменений.

**Результат аудита источников PR-8:** достаточной истории изменений качества классификации с датами в существующих полях нет. Нельзя оценивать лаг реальной реклассификации по датам закрытия, импортам, версиям справочника или текущей доле A/B/C/D. Для реальных данных модель по умолчанию возвращает «недостаточно данных».

## Что реализовано

Изолированная библиотека `src/js/kpi/classification_lag_forecast.js` с контрактом `ReclassifierKpiClassificationLagForecast`:

- `predict(input)` — отдельная оценка возможного **итогового качества того же завершённого месяца**, а не следующего месяца и не накопленного потока заявок.
- `evaluateSnapshot(snapshot,kpiId,input)` — сравнение числителя и знаменателя предоставленного подтверждённого состояния с реальным Snapshot. При несовпадении результат недоступен.
- Алгоритм `revision-lag-median-delta`, версия `0.1.0`: медианная разница в процентных пунктах между ранним и поздним состояниями фиксированного набора обращений. Ограничивает оценку диапазоном 0–100%.
- **Временная причинность:** для каждой исторической проверки разрешены лишь финальные состояния, опубликованные **до** даты более ранней оцениваемой версии. Отсутствующая история не восстанавливается математически.
- Не менее 8 пригодных исторических пар, не менее 4 причинно доступных обучающих пар и не менее 3 исторических проверок. MAE должен быть ниже MAE стратегии «оставить наблюдаемое качество без поправки».
- Каждая пара ревизий описывает одну и ту же популяцию обращений (`populationHash` и одинаковый ненулевой знаменатель), имеет даты и сведения об источниках с ревизиями и хешами. Для качества ЦГПС обязательна также МБ; незаверенное покрытие МБ не считается историей качества.
- Тесты отклоняют конфликтующую популяцию, временную утечку, неверные даты, нестабильный знаменатель, неподтверждённые данные ЦГПС, непригодные истории и ухудшение относительно простого прогноза.

Эти проверки необходимы, но **сами по себе не удостоверяют достоверность файла истории**: при появлении корпоративного источника нужен внешний аудит и проверка ключей обращения, семантики статусов и идентичности популяций.

## Контракт входной истории

```json
{
  "kpiId": "classification_quality",
  "auditBasis": "case-level-versioned-asof",
  "asOf": "2026-10-06",
  "cohortMonth": "2026-09",
  "current": {
    "observedAt": "2026-10-05",
    "successCount": 70,
    "totalCount": 100,
    "populationHash": "hash-of-fixed-case-set",
    "sources": [{"datasetId": "itsm_data", "revision": 3, "contentHash": "source-content-hash"}]
  },
  "history": [
    {
      "cohortMonth": "2025-09",
      "early": {"observedAt": "2025-10-04", "successCount": 60, "totalCount": 100, "populationHash": "same-set", "sources": []},
      "final": {"observedAt": "2025-10-24", "successCount": 70, "totalCount": 100, "populationHash": "same-set", "sources": []}
    }
  ]
}
```

Это иллюстрация структуры, **не загружаемый демонстрационный прогноз**. В настоящем аудите массив `history` должен содержать минимум 8 полностью валидных пар и реальные реквизиты источников в каждом состоянии. Категории A/B/C/D должны быть проверены по фактическому состоянию на дату; история реального изменения должна поступать от соответствующего корпоративного журнала или системы сохранения полных ревизий.

### Где показывается

Вкладка «Динамика и контроль» двух паспортов качества получает дополнительный раздел «Корректировка после реклассификации (экспериментально)». В обычной рабочей сборке он сообщает: **«История изменений с датами не подключена»**. Цифровая оценка появляется только если вызывающий код явно передал `options.lagAudit[kpiId]` с проверенным историческим входом, который совпадает с фактическим Snapshot.

Ни один текущий Dataset автоматически не конвертируется в `lagAudit`. Модуль не читает SQLite и не выполняет сетевые запросы. Загруженные даты обращений и метаданные импорта не используются как даты исправлений.

## Границы PR-8

- Не меняются формулы двух KPI, нормализация классификации, выбор A/B/C/D, приоритет периода, обработка неизвестного статуса МБ, число наблюдений и `Report Snapshot`.
- Ранее существовавший `historical-next-month` с `linear-trend`/`last-value` продолжает работать без изменения настроек PR-4/PR-5.
- Короткий пунктир прогноза незавершённого месяца в графиках трудоёмкости, INC, ВБР/КТГ и цвета не изменяются.
- Текущий прогноз качества на следующий месяц — **совсем другой целевой показатель**. Нельзя объединять их в одно числовое значение или печатать новую оценку в PDF.
- Текущий PDF, Snapshot, HTML-графики, фильтры, Данные и значения KPI не изменены.
- Новая модель не регистрируется под типом существующего прогноза будущего месяца, чтобы не смешать горизонты.

## Что потребуется для боевого lag-aware прогноза

1. Корпоративный журнал изменений классификации или сохранённые полноценные версии строк ITSM с **датой каждой версии**, идентификатором обращения, версиями справочника и результатом инженерной проверки.
2. Для ЦГПС — сопоставимые состояния привязки ITSM↔МБ на дату, с подтверждённым покрытием.
3. Фиксация устойчивого состава каждой исторической популяции, доказуемый хеш состава и аудит недопустимых случаев.
4. Backtesting по датам *as-of*, контроль MAE, доли неполных ревизий, версий модели и решения о допустимости прогноза.
5. Согласование статуса методики и отдельный контракт подключения источника. Только после этого возможно включение модели в полноценные прогнозные сценарии.
