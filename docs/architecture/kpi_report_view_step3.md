# KPI Report View — шаг 3 из 9

**Статус:** расчётный адаптер и внутренняя модель представления подключены; дизайн карточек и паспортов пока НЕ меняется.

## 1. Назначение

Этот этап объединяет уже работающие:
- [KPI Catalog](kpi_catalog_step2.md) — описание и источники показателя;
- Subject Preparation / Calculator — фактический расчёт;
- Report Snapshot — согласованные результаты одного запроса;
- новую чистую проекцию `ReclassifierKpiReportViewModel`.

**Единственный математический источник KPI** — прежний Calculator. Модель отображения не вычисляет официальные показатели из первичных строк, не обращается к SQLite и не реализует альтернативных формул.

## 2. Поток данных

    Runtime Repository → Source Facts → Preparation
      → Calculator / source-missing guard → KPI Results
      → месячные KPI Results для всех 11 реализованных KPI
      → KPI Report View Model (текущее, предыдущее, Δ, forecast-state, series)
      → один immutable Report Snapshot
           ├── results / series.monthly (старый контракт WEB/PDF)
           └── kpiView (новый контракт будущих карточек, графиков, паспортов)

- `src/js/kpi/report_view_model.js` — чистое преобразование **готовых** результатов, вызываемое в `reliability_report_service.js`.
- Список действующих KPI и зависимости от Dataset не дублируются в сервисе: они берутся из `ReclassifierKpiCatalog.list({calculationState:'implemented'})` и `getCalculation(kpiId).sources`.
- `Report Snapshot` принимает дополнительное **опциональное** поле `kpiView`; контракт `schemaVersion='1.0.0'`, старый `results`, `series.monthly` и PDF-связь остаются неизменными. Старые создатели Snapshot, не передающие `kpiView`, получают `null`.
- PDF не читает новые показатели и не инициирует нового расчёта. Совместимость старой выгрузки проверяется CI.

## 3. Контракт `snapshot.kpiView`

| Поле | Назначение |
|---|---|
| `version`, `catalogVersion` | Версии проекции и каталога, чтобы не смешивать разные методики |
| `selectedMonth`, `previousMonth` | Текущий и непосредственно предшествующий календарный месяц |
| `filters` | Тот же запрос по руднику и классу оборудования |
| `cards[kpiId]` | Подготовленная информация для универсальной карточки |
| `seriesById[kpiId]` | Месячная динамика для каждого KPI в доступном диапазоне |

**Структура `cards[id]`:**

`kpiId`, `passportRef` (id/версия каталога/версия Calculation Contract), `current`, `previous`, `change`, `changeUnit`, `changeReason`, `forecast`, `target`, `status`, `sourceRevisions`.

`current` / `previous`: `{value, dataState, reason, period}`. Числа берутся **только** из KPI Results; разность значений вычисляется лишь при двух доступных сопоставимых результатах.

`forecast`: `{value:null, dataState:'not-calculated', reason:'forecast-method-not-defined', horizon:null, methodId:null, change:null}` для действующего KPI. Для не реализованного KPI `dataState='unavailable'` и `reason='kpi-not-implemented'`. Прогноз не равен скользящему среднему и **не** создаётся этим этапом.

`target=null` и `status='neutral'`, пока цели/направления не введены официально. Для процентов `changeUnit='п.п.'`, для часов — `чел.-ч`.

**Структура `seriesById[id]`:** `{kpiId,grain:'month',slice,points}`. Каждая точка: `{period,value,dataState,reason,components,formulaVersion}`. Если в календаре между двумя месяцами отсутствует исходный период, вставляется **недоступная точка** (`null`, `period-not-in-source-calendar`) для корректного разрыва графика. Пробел не превращается в ноль. Длины диапазонов, которые выходят за 1200 месяцев, отвергаются без скрытого обрезания.

### Как определяется «Предыдущее»

**Строго календарный предыдущий месяц**, включая переход январь → декабрь предыдущего года, с тем же набором фильтров. Нельзя подставлять август вместо отсутствующего сентября. При недоступной истории, например при ВБР без исторического Equipment, `previous.value=null`, `change=null`, а `reason` сохраняет причину из Calculator или отсутствие месяца. Необходимо два значения `dataState='available'`.

Проекция не округляет исходные результаты, чтобы не искажать разницу до форматирования. UI позже форматирует числа по единице.

## 4. Паспорт и происхождение числа

`cards[id].passportRef` содержит устойчивую ссылку на **тот же** `ReclassifierKpiCatalog.get(kpiId)`, который позднее откроет modal или страница паспортов. Каталог не копируется внутрь каждого снимка. Наборы `sources` из Calculation Contract определяют список ревизий, доступность, хеш и актуальность соответствующих Dataset. Подлинная поэтапная трассировка (список реально исполненных операций, отсева и SQL/JS) пока отсутствует и вводится только на шаге 8: `sourceRevisions` — это происхождение, не полный KPI Trace.

Сейчас все Calculation Contract по-прежнему имеют статус `draft`. Полноту разметки колонок/фильтров по каждому KPI необходимо проверять с реальным процессором при дальнейшем утверждении паспортов.

## 5. Месячные данные и ограничения

- `series.monthly` остаётся массивом строк `{period,label,sla,classification_quality,vbr,...}`, но содержит **все 11 реальных KPI Results** за исходные месяцы, а не только три. Это позволяет построить 11 рядов **из того же прохода Calculator**.
- Парк Equipment остаётся снимком на дату каталога, не историческим источником. ВБР за другие месяцы имеет штатную недоступность.
- Четырёхмесячное скользящее **пока не рассчитывается**. Его метод задаёт Catalog и будет реализован в окне динамики на шаге 7, строго по компонентам для процентных KPI.
- Дневная/недельная динамика отсутствует. Данных требуемой гранулярности пока нет.
- Для будущего отображения «по рудникам» используются существующие фильтры и запросы нового Snapshot на выбранный рудник. Многорудничное сравнение и его UI — шаг 7.
- Сервис не записывает новую SQLite-таблицу и не меняет физическое хранение Dataset.
- Сервис не считает `previous` по произвольному найденному последнему месяцу и не делает forecast без методики.

## 6. Контроль приёмки

1. Нет дублирующихся списков действующих KPI и зависимостей от Dataset в Report Service.
2. На новом Snapshot доступны все 18 карточек — 11 действующих и 7 неподключённых — и 18 рядов (с `null`, а не вымышленными данными).
3. Для каждого действующего KPI факты в `results[id]`, `kpiView.cards[id].current` и `series.monthly[].id` согласованы.
4. Корректно обрабатываются разные месяцы, пропуски, недоступная история ВБР, январь/декабрь, отсутствующий источник, пустой прогноз, происхождение.
5. Сохранены существующие контракты `results`, `series.monthly`, `breakdowns`, `sources`, PDF, иммутабельность Snapshot.
6. Новые тесты в CI и полная offline HTML + SQLite/Chromium регрессия.
