# Финальная приёмка паспортов и графиков — этап 4 из 4

## Границы выпуска

Проверяется состояние после этапов 1–3: шкала графиков месяц/квартал/полугодие/год сохраняет всю месячную историю; паспорта 18 KPI имеют читаемую структуру; 11 действующих KPI содержат MathML-формулы и условные примеры; семь неподключённых KPI не имитируют расчёты; заголовки ITSM исходят из Field Registry; МБ и Equipment правильно различают исходные поля, производные и метаданные; технические таблицы раскрываются по запросу.

## Приёмка

1. Полный Python/Node регресс, проверка 18 каталожных объектов, 11 формул, KPI Calculator и паспортов.
2. Генерация автономного CORE HTML без встроенных рабочих Dataset и внешних CDN-зависимостей.
3. Проверка наличия финальных текстовых маркеров и контролов в готовом HTML.
4. Фактическая загрузка файла через file:// в headless Chromium с выключенной сетью.
5. Дополнительная проверка в самом Chromium: рендерер паспортов, 18 показателей, 11 формул с MathML, семь корректных заглушек, исходные заголовки ITSM и МБ, четыре масштаба временной оси.
6. Сохранение прежней проверки выгрузки PDF из дашборда и подключения пользовательской SQLite через UI.
7. Публикация релиза только при успешном полном workflow в main, после слияния проверенного PR.

## Что не меняется

Нет новых KPI-формул или алгоритмов реклассификации. Сохраняются Calculation Contract, KPI Results, Snapshot, трассировка, прогноз, Dataset, SQLite и PDF. Шаг 4 — усиление проверок и выпуск.

## Остаточные ограничения

- Семь KPI ещё не реализованы и не получают вымышленные значения.
- ВБР остаётся расчётной относительной оценкой с ограничением статистической интерпретации.
- Шаг «Неделя» недоступен без фактической недельной агрегации.
- Тесты с подготовленными данными не равны бизнес-приёмке цифр на согласованной официальной выгрузке.
- Автономный Chromium на GitHub Runner иногда не стартует и не создаёт DevToolsActivePort: увеличение времени ожидания допускает медленный старт, но не маскирует реальную ошибку приложения.
