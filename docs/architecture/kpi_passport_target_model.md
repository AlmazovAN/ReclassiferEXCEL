# Целевая модель KPI — шаг 1 из 9

**Статус:** проектный контракт 1.0.0 (НЕ утверждённая производственная методика).
**Основа:** [существующая архитектура расчёта KPI](kpi_calculation_contract.md).
**Связанные артефакты:** [машиночитаемая JSON Schema](../contracts/kpi_target_model.schema.json) и [синтетический пример SLA](../contracts/examples/kpi_sla_target_model.example.json).

## 1. Зафиксированный UI

Карточка KPI: **крупное текущее значение**, ниже в три колонки **Предыдущее → Изменение → Прогноз**. Цель и пороги остаются в паспорте. Если прогноз не определён, показывать «—», а не вычислять приблизительно.

Основная область карточки открывает **Динамику KPI**. Отдельная кнопка открывает **Паспорт KPI** как нативный HTML `<dialog>`, а не `window.open()`. В левом меню появляется отдельный раздел **Паспорта KPI**. Модальное окно и страница получают один паспорт по `kpiId` из одного каталога: методика не копируется и не поддерживается в двух местах.

Для динамики на первом этапе: месяцы, **3М / 6М / 1Г / Всё**, один выбранный рудник или «Все рудники» с таблицей для переключения. Дневные/недельные кнопки неактивны, пока факты не имеют соответствующей гранулярности. Фактическая линия и бледная толстая линия оконного показателя (по умолчанию четыре полных месяца; кнопки «−» и «+», минимальное окно два месяца). Прогноз — самостоятельный алгоритм будущих значений, **не** скользящее среднее.

## 2. Сохранённая архитектура

    Processed Datasets (ITSM / MB / Equipment / References)
       → Source Facts
       → Subject KPI Preparation (разные зерна)
       → Pure KPI Calculator
       → KPI Results
       → immutable Report Snapshot
       → WEB и PDF (один Snapshot)

Это уже реализованный расчётный контур. Его **не заменять** новым универсальным KPI Source или скриптом паспорта. `src/js/modules/itsm/kpi_source.js` — вспомогательный месячный агрегат ITSM, а не универсальный источник для расчёта всех KPI.

В частности, результат `vbr` можно фильтровать по `equipmentClass=mounted` или `stationary`; не следует размножать паспорта/формулы как `vbr_mounted` и `vbr_stationary`. Статусы и формулы по-прежнему берутся из существующего Calculator.

**Пять целевых сущностей:**

| Сущность | Источник/владелец | Содержание и задача |
|---|---|---|
| KPI Definition + Calculation Contract | KPI Catalog, шаг 2 | Смысл, единица, цель, версия методики; поля, фильтры, JOIN, подготовка, арифметика, агрегирование и правила времени |
| KPI Result | Существующий Calculator | `id`, `value`, `dataState`, `reason`, `components`, `formulaVersion`, `query`, `sourceComponents` и диагностика |
| KPI Series | Сервис над месячными KPI Results | Значения или явная недоступность за каждый календарный период и тот же срез |
| KPI Trace | Preparation/Calculator + Snapshot provenance | Фактические входы, число строк, реальные компоненты, операции, исключения, версии источников, ключ Snapshot |
| KPI Card View | Детерминированная проекция Snapshot | `current`, `previous`, `change`, `forecast`, `target`, `status` для UI |

Время расчёта `calculatedAt` принадлежит `Report Snapshot`, а не чистому Calculator. Проекция карточки не должна добавлять фиктивные `previous`, `change` и `forecast` прямо в KPI Result. WEB и PDF продолжают читать **один** Snapshot. Прямой доступ UI к SQLite запрещён.

## 3. Паспорт KPI: обязательные блоки

| Блок | Поля и правила |
|---|---|
| Идентификация | `id`, `title`, `category`, `unit`; уникальный стабильный `kpiId` |
| Определение и смысл | `definition`, `purpose`, `direction` (выше лучше / ниже лучше / диапазон / нейтрально) |
| Цель и пороги | `target` и правила интерпретации; `null`, если ещё не утверждены |
| Контроль методики | `methodology.version`, `status=draft/approved/retired`, основание, дата действия |
| Источники и колонки | Каждый `datasetId` и **семантическое** `field`, исходное отображаемое название, роль, политика `null`, откуда поле получается |
| Соединения | Левый/правый Dataset и ключи, `INNER/LEFT/LOOKUP`, кардинальность, отсутствие соответствия, дубли |
| Фильтры и исключения | Поле, оператор, константа или параметр выбранного рудника, стадия, причина включения/исключения |
| Подготовка | Последовательность именованных шагов `FILTER/JOIN/MAP/GROUP/COUNT/SUM/...` с входами и результатами |
| Финальная арифметика | `ADD/SUBTRACT/MULTIPLY/DIVIDE/ROUND`, формула, версия, единица, нулевой знаменатель, точность |
| Агрегация | Базовое зерно, способ агрегации **компонентов**, способ совмещения периодов, пробелы данных |
| Временная логика | Конкретное поле даты, выбор периода, предыдущий сопоставимый период, неполный месяц, историческая доступность |
| Скользящий показатель | Метод, размер окна, необходимость полного окна, обработка пропусков |
| Прогноз | Горизонт, метод и версия, минимальная история, условия недоступности |
| Трассировка | Источники и ревизии, счётчики отсева, значения каждого этапа, итог, snapshot identity |

Название видимой колонки Excel — **подпись**, не первичный программный ключ. Использовать `Field Registry` / семантический контракт подготовленных фактов. Поля разных Dataset нельзя отождествлять только по совпадающему названию.

Паспорт — структурированная декларация и объяснение **существующих реальных обработчиков**. На шаге 1 он НЕ является исполняемым DSL: никаких `eval`, произвольного SQL и независимого движка формул. На шагах 2–3 вводятся связи с реальными handler и тесты соответствия реализации.

## 4. Правила математики и дат

- Для SLA/качества классификации: `100 × Σ(успешных) / Σ(всего)` по всему выбранному окну. **Не** среднее арифметическое готовых процентов.
- Для трудозатрат: сумма только корректных человеко-часов. `missing` и `invalid` не преобразовывать в ноль.
- Для нулевого/отсутствующего знаменателя: `value=null` + машинная причина. Не показывать `NaN`, `Infinity` или ноль вместо недоступности.
- Поле даты различается между KPI/семействами: события отказов — `completedAt`, текущий простой отказа — `createdAt`, SLA и классификация — `closedAt`, трудозатраты — дата факта МБ. Единое поле даты для всех KPI **запрещено**.
- Парк `Equipment_Combined` — **текущий снимок**; исторический ВБР/его 4-месячное окно без исторического парка недоступны (например `equipment-history-required`). `driversByMine` нельзя использовать как знаменатель ВБР.
- `previous` означает непосредственно предыдущий **сопоставимый календарный период**, не предыдущую произвольную имеющуюся точку. При отсутствии истории → `null` с причиной.
- `change = current − previous`. Для KPI в процентах изменение выражается в **п.п.**; для абсолютных значений — в единицах KPI. Знак арифметический, визуальная оценка зависит от `direction`.
- Скользящее вычисляется **по полному окну последовательных валидных периодов**. Для процентов — отношение сумм исходных компонентов, не среднее процентов. Недоступные месяцы создают разрыв, не нулевую точку.
- Прогноз требует явного горизонта и методики. Пока они не утверждены, `forecast.value=null` и `forecast.dataState=not-calculated`. Никаких сгенерированных прогнозов.

## 5. Версии, доказательность и состояния

Методология (`methodology.version`) **не равна** `formulaVersion`, `preparationVersion`, `schemaVersion`, версии HTML или текущей ревизии Dataset. Статус `draft` не превращается в `approved` после успешного расчёта.

У каждого KPI Result сохраняются `available` / `no-data` / `unavailable` / `insufficient` / `not-applicable` / `error` и `reason`. У прогноза собственное `dataState`, позволяющее показать «не рассчитывался» независимо от актуального значения KPI.

**Фактическая трассировка** относится к определённому `kpiId + query + snapshotRef`, содержит источник и ревизию, список отфильтрованных/исключённых строк (счётчики), именованные компоненты/операции и финальное число. Она **не** дублирует весь набор событий и не выдаёт документальное описание за реально исполненные SQL/JS шаги. Пока нет инструментирования расчётного контура (шаг 8), показывать только паспорт и существующие компоненты/диагностику.

## 6. Граница шага 1 и переход к шагу 2

Шаг 1 поставляет только этот документ, машиночитаемую модель с **синтетическим** примером и её контрактный тест. **Не меняет** runtime, Calculator, Dashboard, PDF, SQLite, Schema DB, данные, KPI Source, версию формул или официальные методики.

Следующие шаги: (2) KPI Catalog; (3) связывание с существующим Preparation/Calculator/Snapshot; (4) карточки; (5) modal паспорта; (6) страница паспортов; (7) график/срезы/скользящее; (8) фактический Trace; (9) согласованный прогноз.

### Критерии приёмки

1. Поля и связи пяти сущностей формализованы; один `kpiId` между паспортом, результатом, рядом, трассировкой и карточкой.
2. JSON Schema явно покрывает источники/колонки, JOIN, фильтры, операции, арифметику, даты, сравнение, rolling и прогноз.
3. Синтетический SLA: 9/10 → 90 %, предыдущий 8/10 → 80 %, изменение +10 п.п.; прогноз недоступен. Это **не утверждённая отчётность**.
4. Контрактный тест проходит без зависимостей из PyPI; действующие расчёты/интерфейс не изменены.
5. Документ согласуется с уже реализованными `source_facts.js`, `preparation`, `calculator`, `report_snapshot.js` и контрактом KPI Calculation Architecture.

### Открытые вопросы для последующих шагов

Утверждённые нормативы и владельцы методик; отсутствие технических определений для части KPI; исторические Equipment-снимки; точные правила включения незавершённого месяца; недельная гранулярность; минимальная история, горизонт и метод прогноза. Эти решения в шаге 1 **не подменяются предположениями**.
