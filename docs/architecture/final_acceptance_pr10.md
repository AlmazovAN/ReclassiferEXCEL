# PR 10 — Итоговая регрессионная и эксплуатационная приёмка Reclassifier

## Цель

Закрыть дорожную карту PR 1–9, не переписывая Calculator и не утверждая недоказанное ускорение. Проверить работающий **единый автономный HTML**, расчёт на реальных embedded ITSM/МБ/Drivers, приёмку SQLite, отчёт PDF, переносимость выгрузок, Worker, кэши, SVG Д/Н/М и текущий прогноз ВБР/КТГ.

## Исторический базис и честность измерений

В исходной диагностике PR 1 наблюдались примерные значения на одной офлайн-сборке:

| Операция | PR 1, мс |
| --- | ---: |
| Полный Report Snapshot, холодный | 8695,1 |
| Повторный Report Snapshot из кэша | 0,1 |
| SVG, 6 рядов, 13 месяцев, первый вызов | 116,9 |
| Повторное получение графика | 1,2 |

PR 6 измерял около **8,5 секунды** для первого полного Snapshot: ускорение холодного расчёта пока **не доказано**. Цифры PR 1 и PR 10 получены на возможных разных GitHub Actions runner, версии Chromium, сборках и в разных состояниях памяти. Это не статистически сопоставимый эксперимент. Нельзя представлять их арифметическую разницу как эффект алгоритма. Поддержка отдельного Worker и первичной стадии решает прежде всего вопрос блокировки UI, а in-memory кэши — повторное использование результатов.

PR 10 формирует `dist/acceptance/pr10_metrics.json` — **агрегированные** числовые наблюдения и дельту к базису. Файл создаётся на CI runner; его **числовое содержимое публикуется в постоянном GitHub Actions Job Summary** (без upload-artifact). Отдельный Actions artifact намеренно не создаётся, потому что на аккаунте может быть исчерпана квота хранения артефактов. В него намеренно не попадают заявки, персональные данные, названия рудников/оборудования, фильтры, исходные строки, SQLite или полный Snapshot.

Операционный критерий по времени в этом PR: `reportColdMs`, `reportWarmMs`, графики, первый кадр паспорта и время полной готовности должны быть измерены, конечны и неотрицательны; **жёсткой цифры SLO в миллисекундах нет**, поскольку аппаратная база не закреплена. Warm Snapshot обязан возвращать тот же объект, что и cold, и регистрировать `report.snapshot.cache.hit`. Индексы и KPI cache не должны превышать ограничения. Отдельное утверждение о кратном ускорении не является результатом PR 10.

## Приёмка

| Группа | Проверка / критерий |
| --- | --- |
| Математика | >=13 рабочих KPI побитово сопоставлены в полном Worker и синхронном Calculator на одном источнике/фильтре; трассировка ВБР с реальными компонентами идентична |
| Полная история | Месячные ряды непустые; первичная стадия не кэшируется вместо полной; PDF разрешён только после полной |
| Фильтры | Реальная смена рудника, уход в Database во время расчёта и возвращение в Report; старый Worker не подменяет новый срез; смена класса оборудования; 13 KPI + компоненты трассировки на новом срезе равны синхронному расчёту; сброс восстанавливает `latest/all/all` |
| Кэши | Повторные untraced KPI используют готовые значения; traced запросы делают реальный пересчёт; контроль `cacheSize <= cacheCapacity`, инвалидация по ревизии/источнику |
| SVG | Все Д/Н/М дают одинаковые агрегаты событий в общем окне; сохранено отдельное представление фактов и трудозатрат; проценты ВБР/КТГ не превращаются в дневные; ghost — только при доступном прогнозе текущего месяца и точном совпадении факта |
| Прогноз | PR8 компонентная формула, линейный тренд и MAE; запрет выдать прогноз за факт; ретро-период или отсутствующая история → значение недоступно |
| PDF | Реальная загрузка через UI; валидный PDF 1.4, fingerprint, страницы, JPEG; никакого пересчёта из исходных Dataset внутри PDF renderer |
| Offline | `Network.emulateNetworkConditions(offline=true)`; строго **0** HTTP(S)-попыток для обоих HTML |
| Масштаб и память | >=250 000 строк baseline; измерение размеров HTML, SQLite, PDF; heap по `performance.memory` *если доступно*; отсутствие вымышленного фиксированного порога RAM |

## Инструменты и файлы

- `tests/test_step9_browser_offline.js` — полная CDP-приёмка **исходного** и **экспортированного** HTML без сети, сверка KPI и графиков, сценарии фильтров и статусов, PDF и Reclassifier.db.
- `tests/pr10_acceptance_metrics.js` — строгая числовая схема, фиксированный и документированный исторический базис, без допуска сырого пользовательского содержимого, программные инварианты и артефакт для аудита.
- `.github/workflows/build.yml` — обязательный unit-контракт + полная offline-проверка + публикация агрегатов в **Job Summary** после CI, без расходования GitHub Actions artifact storage.

**Результаты должны интерпретироваться как приёмка функциональных инвариантов, а не сертификация корпоративного продукта.** Reclassifier остаётся локальным прототипом. Внешний корпоративный интеллектуальный модуль классификации — отдельный проект.

## Известные ограничения и следующий долг

1. Первая холодная подготовка может продолжаться несколько секунд. Нет подтверждённого снижения `reportColdMs` в одинаковых аппаратных условиях. Для заявления о производительности нужен контролируемый многократный A/B benchmark, стабилизированные ревизии CPU/Chrome, одинаковый набор Dataset и протокол p50/p95.
2. Передача source pack в Worker дублирует часть памяти. `performance.memory` нестандартен и отражает неполную картину JS-heap, включая отдельные Worker/SQLite WASM.
3. Дневные/недельные графики относятся только к завершённым INC и проверенным часам; для ВБР/КТГ действуют месячные знаменатели.
4. Прогноз текущего месяца использует текущую численность Drivers и непроверенную полноту дня. Для будущего месяца исторический состав оборудования неизвестен.
5. Материализованные агрегаты не записываются в SQLite — отсутствуют отдельные утверждённые схема ревизий и контракт инвалидации.
6. GitHub Actions проверяет Chromium в Linux и набор встроенных данных. Работу на корпоративных компьютерах, включая конкретные браузеры/политики и ограничения диска/памяти, необходимо подтвердить отдельно.

## Итоговый критерий решения

**ПРИНЯТЬ** только при полностью зелёном CI для HEAD PR, успешном offline Chromium, нуле HTTP(S), совпадении KPI и отсутствии пропажи данных после полного цикла SQLite/HTML/PDF. Если какой-либо тест не пройден, не сливать PR в `main`; зафиксировать причину.

После успешного merge это завершает запланированные 10 этапов технической дорожной карты. Это не означает готовность к внедрению в корпоративную ИС и не присваивает методике экспериментального прогноза официальный статус.
