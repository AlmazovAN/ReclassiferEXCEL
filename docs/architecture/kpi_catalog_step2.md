# KPI Catalog — шаг 2 из 9

**Реализованная часть:** единый программный read-only реестр KPI, паспортов и декларативных Calculation Contracts поверх текущих математических модулей.
**Статус всех методик:** draft. Цели, пороги и прогнозы не утверждены и не подменяются демонстрационными цифрами.
**Основа:** [целевая модель (шаг 1)](kpi_passport_target_model.md) и [принятая архитектура расчётов](kpi_calculation_contract.md).

## 1. Ключевые правила

- Реальные математические формулы/версии/компоненты остаются **только** в `src/js/kpi/calculator/definitions.js`. Каталог **ссылается** на них и проверяет идентичность при запуске.
- Реальные алгоритмы событий, связей и сумм остаются в `src/js/kpi/source_facts.js`, `preparation/*`, `calculator/*`. Паспорт указывает на реальные функции: произвольное исполнение текста через `eval`, SQL или новый движок расчётов отсутствует.
- Паспорт включает: `definition`, `calculation.sources` (поля и роли), `calculation.joins` (кардинальность и дубли), `calculation.filters` (включение/исключение и область действия), `calculation.steps` (порядок и арифметика), `aggregation`, `temporal`, `formula`, `sourceComponents`, версии и `methodology.status`.
- Один `kpiId` для навесного/стационарного ВБР. Рудник/класс оборудования остаются измерениями запроса.
- Для нерезультативных KPI формулы, источники и прогнозы не выдумываются: `calculationState = not-implemented`, `calculation = null`.
- Порог/цель `target = null`. `direction = neutral` для KPI, где направление оценки не является самодостаточно определённым. Цветовое отображение пока не подключено к каталогу.
- **Парк Drivers не имеет помесячной истории:** у ВБР `historicalSupported=false` для ретроспективной оценки на базе **фиксированного справочника Drivers**, `rolling.method=unavailable`. Текущая ревизия справочника применяется ко всем выбранным месяцам, а не интерпретируется как исторический снимок.
- У коэффициентов SLA/качества/долей — сумма числителей / сумма знаменателей при расширении периода; у абсолютных трудозатрат — сумма часов.
- Все записи глубоко неизменяемые и включены в offline HTML. Новая SQLite-таблица и изменение DB Schema не требуются.

**Публичный API:** `globalThis.ReclassifierKpiCatalog`.

- `version`, `ids`, `groups` — версия и полный состав;
- `get(kpiId)` — неизменяемая запись `{ id, visibleInReport, calculationState, definition, calculation }` или `null`;
- `getCalculation(kpiId)` — контракт или `null`;
- `list({ category?, calculationState? })` — список (категория `dataQuality`, `technicalReliability`, `organizationalReadiness`, `labor`, `problemManagement`).

Включается в offline HTML всегда; отдельной загрузки JS/JSON по сети нет.

## 3. Проверенный охват

**Всего 18 KPI**, из них **17 карточек** в текущем шаблоне отчёта и один расчётный, ещё не выведенный на карточку — `avr_share`.

| Категория | Реально рассчитываемые KPI | Пока без расчётной методики |
|---|---|---|
| Данные и качество | `classification_quality` | `required_fields_completeness`, `confirmed_failures_share`, `data_freshness` |
| Техническая надёжность | `vbr` | `ktg` |
| Организационная готовность | `sla` | `kog`, `service_level` |
| Трудозатраты | `total_labor`, `avr_labor`, `avr_share`, `maintenance_labor`, `corrective_labor`, `reactive_share` | — |

Итого **11 действующих реализаций**, **7 неподключённых**. Наличие контрактной записи **не утверждает** методику или правильность исходных данных.

## 4. Связи, требующие особого внимания

**ВБР.** Суммируются учтённые отказы ITSM и отдельно количество шт. из Drivers в разрезе физического рудника, сервиса и наименования из ITSM (`Наим1`); `Все рудники` и нештучные показатели исключаются. Дата события — `completedAt`, иначе `closedAt`. Тип обращения `INC после рекласс = INC`, решение `ИсклВБР-Спутник = Считать отказом`. Для нескольких месяцев знаменатель = количество по Drivers × число календарных месяцев; это оборудование-месяцы на основе фиксированного актуального справочника, а не архив динамики парка. `itsm_data.driversByMine` не используется — значение повторяется на каждой заявке.

**SLA.** Числитель/знаменатель строятся по `slaState`, получаемому из `slaOverdue`. Последний может поступать из сохранённого полного ITSM Dataset («Просрочен по разрешению»). При неизвестном SLA обращение не входит в знаменатель; период определяется `closedAt`.

**Problem Management.** Связь задач МБ с ITSM выполняется по номеру обращения (`mobile_brigade_data.request` ↔ `itsm_data.number`). Не сопоставленные задачи остаются в общей трудоёмкости; конфликтующие PRB для одинакового номера ITSM получают `ambiguous`, не добавляются в числитель. Связь не размножает строки МБ. Время — дата факта задачи МБ. Фильтры `finalTaskType` и `problemLinkState` могут относиться **только к числителю**, не уменьшая знаменатель.

**Трудозатраты.** Из `mobile_brigade_data` берутся семантические `laborHours`, `laborState`, `finalTaskType`, `factDate`, принадлежность руднику и оборудования. В часы входят только `valid` и `valid_zero`; `missing/invalid/legacy_unknown` выводятся в диагностику, не считаются нулём.

## 5. Граница поставки и следующий шаг

**Шаг 2** не меняет `KPI Result`, формулы, сам Dashboard, PDF, Snapshot, Dataset, SQLite или значения отчёта. UI пока продолжает формировать краткую методику из результата, а каталог существует как отдельный проверенный контракт. Это временная граница, не два независимых источника формул.

**Шаг 3:** подключить новый каталог к Report Snapshot/адаптеру и выстроить единую проекцию для WEB/PDF, не нарушив чистоту Calculator. После этого менять карточки и подключать разные паспортные представления в шагах 4–6.

**Отложенные решения:** утверждённые паспорта, цели и пороги, поведение неполного месяца, официальная помесячная история парка, шаг/горизонт прогноза, точные персональные фильтры для ещё не реализованных KPI. Все остаются `draft`/`not-implemented`.
