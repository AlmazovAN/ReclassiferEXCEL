# PR 6 — Повторное использование KPI Result и индекс временных компонентов

## Цель
Уменьшить число повторных проходов по подготовленным данным при построении отчётов, паспортов и графиков, сохранив Calculator как **единственный источник математических значений**. Не менять формулы, правила подбора отказов, расчёт числителей и знаменателей, контроль источников, статус доступности и трассировку.

## Было
- `KPI Preparation` кэшируется по ревизии, Report Snapshot — до 8 штук, месячные ряды — до 8, точки графика — до 4096. Но при новых комбинациях фильтров одно и то же значение отдельного KPI могло заново проходить через Calculator.
- `CalculatorCommon.selectRows()` индексировал месяцы и отдельные измерения, но после месячного отбора первый фильтр `mine`/`equipmentClass` обычно снова выполнялся полным проходом по месячному набору.
- Для аудиторской трассировки Calculator обязан выполнить реальные `selectRows` и фильтрацию, а не воспроизвести ранее сохранённый trace.

## Стало
1. В `KPI Computation Service` создан in-memory LRU на **2048 отдельных готовых KPI Result**. Это реальные immutable результаты прежнего Calculator (вместе с исходными компонентами), не суммы/средние процентных значений. Запросы ключуются периодом, канонически упорядоченными фильтрами, доступностью источников и ID KPI. Нестандартные запросы, не допускающие надёжного ключа, вычисляются без кэша.
2. При пакетном запросе вычисляются **только отсутствующие** KPI; совпадающие результаты собираются из кэша. При любом запросе `trace` **все KPI рассчитываются заново** — реальные стадии, счётчики, диагностика и события сохраняются, а новый результат может использоваться далее исключительно для запросов без трассировки.
3. Подготовленный bundle зависит от явной source revision + идентичности 4 Dataset. `invalidate()` и замена bundle безусловно очищают result cache. Проверки источников и статусов участвуют в cache key. Версия Calculator контролируется.
4. Для замороженных component tables `CalculatorCommon.selectRows` лениво создаёт индекс комбинации «месяц + первое скалярное измерение» на базе исходного **порядка строк**, а не агрегирует проценты. При массиве значений, диапазоне месяцев, следующем измерении или нестандартных таблицах используется прежняя фильтрация. Индекс ограничен 16 LRU-комбинациями на таблицу; освобождается вместе с таблицей через WeakMap.
5. В разделе «Журнал» отображаются только численные показатели кэша главного потока и Worker (размер, попадания, промахи, вытеснения). Никаких имён рудников, значений фильтров, исходных строк, временных ключей в профиле.
6. В реальном автономном браузере снимаются необязательные сравнимые значения JS heap перед/после повторных запросов (если Chromium поддерживает API). **Абсолютные ускорения/пределы памяти не декларируются** на основании изменчивой среды CI.

## Безопасность и границы
- Никакой записи агрегатов в рабочую SQLite: без единой транзакции версии источников и формулы есть риск устаревших процентов. После замера относительной экономии памяти/CPU можно отдельно принять решение о материализованных производных таблицах в БД.
- Защита от двойного учёта остаётся у исходных Calculator. Никакого усреднения KPI по рудникам/месяцам, пересчёта ВБР/КТГ или изменения источников.
- Не вводится TypeScript, сторонняя графическая библиотека, новая схема Dataset или файловый импорт.
- Исторические месячные ряды сохраняют исходную формулу для каждого месяца и фильтра.
- KPI Result cache относится к локальному экземпляру вычислительного процесса. Его значения не являются результатом независимого расчёта.

- `tests/test_kpi_computation_service.js`: совпадение KPI, cache hits/misses, использование traced vs untraced, source availability guard, несовместимость ревизий.
- `tests/test_kpi_materialization_pr6.js`: равенство `selectRows` для замороженной индексируемой и неизменённой неиндексируемой таблицы, порядок, stage counts, диапазоны и исключения.
- Полный набор регрессий ВБР/КТГ/SLA/трудозатрат/качества классификации, SQLite, HTML и PDF.
- `tests/test_step9_browser_offline.js`: численные результаты всех 13 реализованных KPI совпадают с прежним Calculator, фактическая трассировка сохраняется; в живом Worker два последовательных untraced запроса используют кэш, а `size <= capacity`.
