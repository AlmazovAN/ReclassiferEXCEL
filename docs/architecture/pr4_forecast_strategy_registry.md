# PR-4. Forecast Strategy Registry

**Назначение:** единый реестр и маршрутизатор уже существующих методов прогнозирования Reclassifier. Это архитектурный этап: пользовательский выбор стратегии появится в PR-5.

## Что остаётся неизменным

- Формулы KPI и каждый Calculator.
- Вычислительная математика `forecast_engine.js` (MAE, правила качества, прогностические компоненты, округление, предупреждения, отказ при отсутствии данных).
- Условия полноты и подтверждения среза `reportingCoverage`.
- Прогнозное значение и `methodId` для прежних входных данных.
- Отдельные фактические/прогнозные значения в Report Snapshot.
- Сплошные линии факта, пунктир `5 4`, точка факта, цветовые схемы, фильтры, PDF.

## Стратегии

| ID стратегии | Где действует | Допустимые встроенные методы | Статус |
|---|---|---|---|
| `historical-next-month` | Остальные реализованные KPI с историей | `linear-trend`, `last-value` | Подключена через прежний `predict()` |
| `reporting-month-components` | ВБР, КТГ | `observed-run-rate`, `last-value`, `linear-trend` | Подключена через прежний `predictReportingMonth()` |
| `reporting-month-volume` | Виды трудоёмкости и операционные INC/трудоёмкость | `observed-run-rate`, `last-value`, `linear-trend` | Подключена через прежний `predictReportingMetric()` |

Декларация используется из `ReclassifierKpiCatalog.getV2(id).forecast.policy`. Шесть не реализованных показателей остаются `none`: активную стратегию для них реестр не объявляет.

`reporting-month-components` применяет формулу KPI к прогнозируемым составляющим. `reporting-month-volume` оценивает абсолютный итог месяца. `historical-next-month` является отдельным историческим прогнозом: он **не рисует прогноз итога незавершённого месяца**.

Метод по умолчанию прежний: `linear-trend`, либо `observed-run-rate` при `coverageBasis=observed-event-horizon`. Последняя подмена выполняется самим действующим Forecast Engine; реестр не переписывает входы.

## API

`ReclassifierKpiForecastEngine.strategyRegistry`:

- `list()`: замороженные описания зарегистрированных стратегий;
- `forKpi(kpiId)`: текущая стратегия, версия, политика и методы, либо null;
- `forMetric(metricId)`: стратегия для абсолютных INC/трудоёмкости;
- `predictForKpi(input)`: диспетчер на существующий алгоритм по Definition V2;
- `predictForMetric(input)`: диспетчер для операционных абсолютных показателей;
- `registerStrategy(config)`: регистрация новой стратегии разработчиком;
- `assignKpi(kpiId,strategyId)`: явное назначение совместимой индивидуальной стратегии;
- `restoreDefault(kpiId)`: возврат к встроенной стратегии.

`ReclassifierKpiForecastEngine.createStrategyRegistry()` создаёт независимый реестр для тестов/интеграционных экспериментов. По умолчанию штатный реестр содержит ровно три встроенные стратегии и **не назначает индивидуальных обработчиков**.

При регистрации индивидуальной стратегии обязательны `id`, `version`, `policy`, `methodIds`, `kpiIds` и функция `predict(input)`. Стратегия может быть назначена только разрешённым KPI той же прогнозной политики. Дубликаты/некорректные определения отклоняются.

Результат индивидуальной стратегии проверяется перед публикацией. Недопустимые значения, отрицательные объёмы, проценты за пределами 0–100 и неправильный месяц переводятся в `dataState: unavailable` с причиной `forecast-strategy-invalid-result`. Факт KPI не пересчитывается.

**Граница безопасности:** регистрация — программный API доверенного кода разработчика, не пользовательский редактор JavaScript и не разрешение на сетевую загрузку плагинов. Персональные настройки выбора для интерфейса и Snapshot — PR-5. Нельзя незаметно изменять официальную методику.

## Точки подключения

- `src/js/kpi/report_view_model.js`: единое определение метода для Report Snapshot и помесячного ряда, без дублирования процентного и абсолютного вызова.
- `src/js/app/reliability_report_service.js`: тот же диспетчер для графиков с точными фильтрами рудника/класса/оборудования и для операционных INC/трудоёмкости.
- `src/js/kpi/forecast_engine.js`: сам реестр поверх существующих методов. В Worker он доступен из того же файла; менять состав и порядок скриптов `build.py` не требуется.

## Тестирование и приёмка

`tests/test_kpi_forecast_strategy_registry_pr4.js` сверяет реестр и Definition V2 для всех 19 KPI, сравнивает результаты старых методов с реестром по полному объекту (`deepEqual`), проверяет разные политики, доступность, и изолированную регистрацию индивидуального алгоритма (без включения его в приложение).

Продолжают действовать PR-1, PR-2 и PR-3, численные тесты ВБР/КТГ/INC/трудоёмкости, существующие SVG-регрессии, PDF и offline Chromium.
