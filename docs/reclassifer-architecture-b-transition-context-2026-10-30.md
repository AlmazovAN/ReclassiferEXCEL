# Reclassifer — архитектурная перестройка, вариант B

Дата: 30.10.2026. Тип: переносимый контекст для нового чата и проектирования. Статус: выбранное направление, а не готовая спецификация реализации. Репозиторий: https://github.com/AlmazovAN/Reclassifer .

## 1. Цель и ограничения

Reclassifer — локальное браузерное HTML/JavaScript-приложение для анализа корпоративных Excel/Dataset, реклассификации, Мобильных бригад, ITSM, оборудования, KPI, дашбордов и экспорта. Рабочий сценарий — один HTML, Opera, часто локальный запуск через file://, без установки дополнительного ПО и без передачи корпоративных данных вовне.

**Принято направление B:** перейти от локального устранения симптомов OOM к архитектуре управления данными: единый Data Access Layer, SQL-проекции и страницы, координатор задач, backpressure, Worker, контроль жизненного цикла памяти. Не переписывать приложение одномоментно и не отказываться от SQLite до сравнения альтернатив.

Не считать заранее, что OPFS, SAH pool, File System Access API или локальный HTTP-сервер доступны в целевой корпоративной Opera из file://. Поддержка и безопасный fallback требуют эксперимента.

## 2. Текущее устройство

- Excel: Dataset Recognizer → проверка и нормализация → подготовка плана UPSERT/REPLACE → preview по SQLite → ручное подтверждение → транзакционный COMMIT → Runtime sync.
- SQLite: локальный .db → ArrayBuffer → SQLite WASM/VFS → Repository → объекты JS records/Full Dataset → Runtime caches → интерфейсы, KPI Worker, экспорт.
- Возможны одновременные крупные выделения: SQLite WASM, входной буфер, JS-массивы, кандидаты, XLSX и память Worker. Это **гипотеза OOM**, не доказательство конкретной утечки.
- COMMIT внутри браузера не равен гарантированной записи обновлённого .db на диск. Сохранение/восстановление остаются самостоятельными пользовательскими сценариями.

## 3. Что подтверждено тестами

### TEST_17 / PR #332
Курсорное чтение SQLite JSON вместо накопления промежуточных строк. Отдельный путь KPI: для Мобильных бригад — аналитические records без Full Dataset; для ITSM — SLA-проекция вместо полного row_json. Оптимизировано повторное использование массивов в Runtime caches. **Остаётся:** сами аналитические records иногда материализуются целиком и передаются в Worker.

### TEST_18 / PR #335
Диагностика scoped по HTML, ограничение 4 сессии × до 384 событий, агрегирование попаданий runtime-cache вместо тысяч WAL-событий. Полный Codespaces прогон: TOTAL FAILED CHECKS: 0; создан Reclassifier_v0.37.0_CORE_TEST_18_PR335.html (5,4 MB). Тестовый Runtime JSON от 30.10.2026: 226 162 байта, 4 архивные сессии, storageFailures=0, walPending=0, globalSeq=1070. Для сравнения журнал TEST_17: 5 671 634 байта, 52 227 storage failures. Оптимизация **журнала** подтверждена; устранение OOM не доказано.

### Зафиксированные ограничения
- SQLite WASM capacity около 912 MiB; это **не RSS** браузера.
- В последней сессии TEST_18 — 26 материализаций и 1 178 923 строк **суммарных чтений**, не уникальных записей.
- Другие потребители по-прежнему способны загружать большие МБ/ITSM в JS, несмотря на отдельный облегчённый путь KPI.
- Файл tasks_2026-01-01_2026-09-04 (1) РО РС.xlsx (13,03 MB, 37 764 строки) несколько раз обрабатывался после аннулирования кандидатов при параллельных COMMIT. Последняя подготовка завершилась; UI мог продолжать показывать «В очереди…». Требуется проверить разницу между фактическим состоянием и индикатором.
- Есть зарегистрированная ошибка фонового расчёта KPI; точная первопричина не локализована.
- Метрики performance.memory и sampled main JS heap не измеряют полную память браузера, Worker и SQLite.

Гипотеза «из старой архитектуры выжато всё» **не доказана**, но дальнейшие оптимизации требуется профессионально структурировать, а не вести как бесконечную цепь симптоматических исправлений.

## 4. Концепция целевой архитектуры

1. UI / Presentation — страницы, фильтры, метаданные, прогресс и ограниченные выборки. Не хранит длительно полные многосоттысячные Dataset.
2. Query / Job Coordinator — приоритеты, отмена, сериализация конфликтующих операций, backpressure, memory budget, revision, operationId, прогресс.
3. Database Worker — SQL-запросы, транзакции, управляемая выдача страниц/агрегатов. Не возвращает в UI весь Dataset по умолчанию.
4. Import Worker — чтение/нормализация Excel по партиям. Нормализацию файла отделить от зависящего от ревизии базы UPSERT-preview.
5. Export Worker — порционная генерация файлов с ограничением потребления памяти.
6. Data Access Layer / Repository — единые контракты: список Dataset, метаданные, ревизии, SQL-проекции, агрегаты, страницы, подготовка/COMMIT/откат, история операций.
7. Авторитетное локальное хранилище — пока SQLite, с исследованием SQLite Worker + MEMFS или file-backed OPFS/SAH в реальном режиме Opera file://. Выбор альтернатив без SQLite — отдельное архитектурное решение.
8. Диагностика — bounded, независимая от корпоративного содержимого; причины отмены, стадии и ограничения памяти.

**Инвариант:** перенести прежний full getDataset в Worker недостаточно: нужно ограничить объём данных на границе API, иначе крупные JS-массивы сохранятся или будут клонироваться.

## 5. Неприкосновенные требования

- Не менять бизнес-логику реклассификации, SLA, формулы KPI, правила UPSERT/REPLACE, дедупликацию, типы, порядок, ключи, исходные колонки.
- Не терять данные SQLite, импортную историю, восстановление, ручное подтверждение COMMIT и rollback.
- Не терять уже внесённые в main изменения интерфейса, журнала, навигации и дизайна.
- Не передавать корпоративные базы и исходные XLSX в публичный GitHub; все проверки на копиях.
- Сохранять автономный HTML и отсутствие обязательной установки ПО; если предлагается новый режим развёртывания, отдельно обосновать его совместимость.
- Разделять факты, оценки и гипотезы; не выдавать WASM capacity за RSS. Никаких обещаний «OOM полностью устранён» без воспроизводимых замеров.

## 6. Сначала аудит (этап 0), затем программирование

Подготовить документ архитектурного обследования:

1. Карта хранения и потоков данных: SQLite → Repository → Runtime → UI/KPI/Export; места загрузки полных records/Full Dataset, копирования/structured clone.
2. Карта памяти на неизменной копии БД: WASM, VFS, исходный ArrayBuffer, JS heap, Worker, кеши, XLSX, кандидаты. Для одинаковых сценариев отдельно фиксировать peak RSS/Memory Footprint Opera, after-GC и удерживаемые объекты.
3. Карта импортных транзакций: inspect → prepare → diff → confirm → commit → refresh → запись .db; где меняется ревизия и почему кандидаты повторно парсятся.
4. Матрица возможностей среды: Opera, file://, Worker, OPFS/SAH, IndexedDB, разрешения на файлы, аварийное восстановление.
5. Golden dataset и эталонные KPI/импорт/экспорт: одинаковые исходные данные, даты, фильтры, значения. Сравнение чисел и порядка, а не только отсутствия исключений.
6. Решение о целевой архитектуре и оценка стоимости миграции, рисков для сохранности, совместимости и отката.

## 7. Предлагаемая дорожная карта — отдельные Draft PR

| Этап | Содержание | Приёмка |
|---|---|---|
| 0 | Аудит и baseline памяти | Отчёт с воспроизводимыми RSS/peak и картой источников |
| 1 | Data Access Layer и Job Coordinator | Контрактные тесты, управление ревизиями и отменой |
| 2 | SQL-projection и постраничные API | Меньше Full Dataset, численно те же KPI |
| 3 | Прототип SQLite Worker / file-backed storage | Сравнение MEMFS и OPFS/SAH на реальной Opera file:// |
| 4 | Импорт и очередь Excel: normalize отдельно от diff | Не парсить XLSX заново после каждого COMMIT, сохранить rollback |
| 5 | Экспорт, снимки, сохранение и recovery | Результаты идентичны эталону, восстановление проверено |
| 6 | Миграция, интеграция и удаление дублирующих путей | Полная регрессия, стресс-тест на копии SQLite, план отката |

Порядок этапов 2–4 уточняется после аудита. Целевое снижение RSS/времени устанавливается только после baseline. Каждый этап должен иметь измеримый результат и самостоятельный безопасный rollback.

## 8. Отдельная альтернатива: работа без SQLite

У пользователя есть идеи о системе вообще без базы. **Не отвергать и не принимать их заранее.** В следующем чате обсудить конкретный сценарий и сравнить: SQLite с новым API/Worker; файлы Dataset/индексы; гибрид с подготовленными проекциями; браузерное хранилище (при наличии поддержки). Сравнить скорость поиска, UPSERT/rollback, объёмы 250 тыс.+ строк, переносимость одного HTML, RAM, сохранность и сопровождение.
