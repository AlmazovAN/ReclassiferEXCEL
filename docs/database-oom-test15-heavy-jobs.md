# TEST_15_PR324 — координация тяжёлых операций и корректное восстановление журналов

**PR:** https://github.com/AlmazovAN/Reclassifer/pull/324  
**Ветка:** `feature/test15-heavy-job-coordination`  
**База:** `feature/pr322-sqlite-mb-paged-xlsx-export` (stacked Draft PR #322, не main).

## Основание

В TEST_14 наблюдалась одновременная работа автоматического KPI (~74,6 с)
и экспорта XLSX. Простое `AbortController.abort()` не гарантирует остановку
уже запущенного WebWorker: `KpiTaskScheduler` прекращает ждать результат,
но физически Worker продолжал обрабатывать данные.

## Реализовано

- `ReclassifierHeavyJobGate` даёт **одну аренду** для SQLite XLSX или импорта.
- Если работает только **автоматический KPI (priority 5)**, gate сначала
  приостанавливает планировщик автообновления, затем завершает KPI Worker
  через `KpiBackgroundJobs.preemptAuto()`. Отменённое задание не публикует
  результат. После освобождения аренды незавершённый KPI планируется снова.
- Если работает интерактивный KPI (priority 0–4) либо ожидают задания,
  импорт/экспорт **не стартует** и показывает сообщение. Интерактивный
  KPI принудительно не прекращается.
- При активном импорте/экспорте новые фоновые и интерактивные
  `buildSnapshotAsync` / `calculateKpiAsync` не запускаются.
- В очереди KPI закрыта гонка: отменённая после выбора, но до первого
  микротакта задача не должна запускать Worker.
- Runtime журнал TEST_15 создаёт отдельные сессии для импорта,
  последующего KPI и повторного открытия HTML.
- Восстановление метаданных сессий только из WAL использует последнюю
  доступную редакцию по `eventCount`; итоговый `prepared`/время завершения
  не заменяются ранним `running`.
- TEST_15 наследует TEST_14 metadata-first Runtime и KPI hot-cache и
  TEST_13 IndexedDB + синхронный localStorage WAL.

## Сохранённые контракты

Не менялись формулы KPI, SQLite схема/ревизии, Full Dataset,
состав колонок и формат XLSX, алгоритмы классификации, обработка
`candidate-records`. Реальный эффект по OOM ещё не подтверждён:
первая сборка KPI по-прежнему использует крупные источники, а для
больших XLSX нужен отдельный тест на 10–12 тысяч строк и 38 колонок.

## Сборка и регрессии Codespaces

```bash
cd /workspaces/Reclassifer
git fetch origin
git switch feature/test15-heavy-job-coordination
git pull --ff-only origin feature/test15-heavy-job-coordination
bash tests/run_test15_codespaces.sh
```

Скрипт выполняет JS и Python guardrails и собирает
`dist/*_CORE_TEST_15_PR324.html` **только если все тесты прошли**.
Полный журнал: `diagnostics/TEST_15_codespaces_<UTC>.log`.

## Проверка в Opera

1. Открыть собранный HTML из того же каталога/профиля, что и TEST_14,
   и подключить копию SQLite (≈860 MiB).
2. Запустить KPI, дождаться `kpi-auto-calculate/start`, затем
   экспорт Full Dataset МБ. В Runtime журнале должны появиться
   `kpi-auto-preempted`, `heavy-job-start`, `heavy-job-end`.
3. Проверить, что после XLSX автоматически продолжается KPI
   (или используется полный подтверждённый Snapshot), и сравнить
   результаты KPI с TEST_14 на той же базе.
4. Проверить ручной KPI в процессе: экспорт должен отказать без
   остановки интерактивного KPI и без повреждения данных.
5. Выполнить импорт XLSX (~55 тыс. строк) в копию SQLite;
   в JSON `prepared`/время завершения должны относиться только к
   сессии импорта, последующие KPI-события — к `observing`.
6. Сохранить два JSON (Runtime и XLSX). Закрыть вкладку, снова открыть
   **тот же HTML в том же браузерном профиле** и проверить старые
   сессии, `idbStatus`, `walPending`, `completenessKnown`.
7. Повторить XLSX для января 2025 с ожидаемыми примерно 11,6 тыс.
   строками, чтобы проверить именно объёмную сериализацию.

Предел гарантии: WAL/IndexedDB зависят от доступности localStorage,
browser quotas, защиты `file://` и аварий ОС. Сборка не заявляет
абсолютную устойчивость хранения после потери дисковых операций.
