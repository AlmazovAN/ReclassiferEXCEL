# SQLite Database Architecture Contract

## 1. Назначение

Этот документ фиксирует целевой контракт разделения Reclassifier на две независимые части:

- `Reclassifier.html` — приложение;
- `Reclassifier.db` — переносимая SQLite-база данных.

Стабильный Dataset-контракт (`id`, `kind`, Dataset Schema, `allowEmpty`, `persisted`, strategy, `keyField`, `partitionField` и derived-зависимости) хранится в едином `src/js/app/dataset_catalog.js`. `database_contract.js` строит из него SQLite Dataset Contract, поэтому runtime и БД не должны иметь независимые копии этих свойств. DB Schema и Repository-контракт были зафиксированы на этапе 1. В версии приложения 0.24.0 работает официальный SQLite WASM 3.53.4: приложение создаёт, открывает, проверяет, изменяет и экспортирует `Reclassifier.db`. При открытой БД SQLite-first Runtime Repository является единственным источником сохраняемых Dataset; отдельный HTML Dataset Store сохраняется как самостоятельный режим, пока БД не открыта.

## 2. Основной принцип совместимости

Версия приложения, версия схемы SQLite и версия конкретного Dataset — независимые величины.

Текущие версии (релиз 0.24.0):

- App Version: `0.24.0`;
- DB Schema: `1`;
- ITSM Dataset Schema: `1.1.0`;
- Mobile Brigade Dataset Schema: `1.4.0`.

Изменение колонок отдельного Dataset не должно автоматически требовать изменения DB Schema.

При появлении новых версий DB Schema миграции должны идти последовательно (например, в будущем `1 → 2 → 3 → 4`). Пока реализована DB Schema 1; этот пример не означает, что схемы 2–4 уже существуют.

Помимо DB Schema приложение проверяет логический контракт `dataset_registry` против текущего Dataset Catalog. Для каждого persisted Dataset должны точно совпадать `kind`, Dataset Schema, стратегия интеграции, `keyField`, `allowEmpty` и `persisted`. Отсутствующий обязательный Dataset, неизвестный Dataset или любое расхождение этих полей делает базу несовместимой с текущей версией приложения до явной миграции Dataset-контракта.

Старая версия приложения не имеет права писать в БД с более новой схемой или с неизвестным ей Dataset-контрактом.

## 3. Идентификация файла

Каждая рабочая база использует:

- SQLite `PRAGMA application_id = 0x52434C46` (`RCLF`);
- SQLite `PRAGMA user_version` как авторитетную версию DB Schema;
- `app_metadata.database_type = reclassifier-sqlite`;
- уникальный `database_uuid`.

Файл, не прошедший эти проверки, не должен открываться на запись.

## 4. SQLite Schema v1

Системные таблицы:

| Таблица | Назначение |
|---|---|
| `app_metadata` | Паспорт файла БД и версия схемы |
| `dataset_registry` | Реестр Dataset и их активное состояние |
| `dataset_records` | Универсальное построчное хранилище |
| `dataset_state` | Метаданные и дополнительное состояние Dataset |
| `import_history` | Аудит загрузок и интеграций |
| `schema_migrations` | История миграций структуры БД |

Полный DDL является машинно-читаемой частью `src/js/app/database_contract.js`; Dataset metadata для Registry берётся из `src/js/app/dataset_catalog.js`.

## 5. Почему Dataset хранятся универсально

Физическая SQLite Schema не должна повторять все бизнес-колонки ITSM, МБ и справочников.

`dataset_records` хранит:

- `dataset_id`;
- `record_key`;
- `ordinal`;
- `record_json`.

Это позволяет менять Dataset Schema независимо от структуры SQLite и не создавать миграцию БД при каждом добавлении аналитической колонки.

Для Dataset с UPSERT `record_key` равен устойчивому бизнес-ключу.

Для Dataset с REPLACE ключ является технической идентичностью строки внутри новой полной ревизии; старая ревизия удаляется транзакционно.

`dataset_state` предназначен для состояния, которое не является обычной строкой Dataset: метаданные, freshness, индексы и иные данные, необходимые для восстановления активного экземпляра.

## 6. Стратегии интеграции

### UPSERT

Используется для накопительных событийных Dataset:

| Dataset | Dataset Schema | Ключ |
|---|---:|---|
| `itsm_data` | 1.1.0 | `number` |
| `mobile_brigade_data` | 1.4.0 | `recordKey` |

Правило:

- существующий ключ — заменить свежей строкой;
- новый ключ — добавить;
- записи, которых нет во входной партии, не удалять.

### REPLACE

Используется для статичных справочников и исходных каталогов Equipment:

- Reclassification;
- Drivers;
- Customers;
- TypeRequest;
- Initiators;
- Exceptions;
- ProblemGrade;
- пять Equipment sources;
- Failure Classifier.

Новый Dataset сначала полностью распознаётся и валидируется. Для обычного REPLACE старая активная версия заменяется новой в одной транзакции. `CatalogStationaryEquipment` использует секционный REPLACE по `unit`: заменяются только рудники, присутствующие во входном снимке, остальные секции сохраняются.

### DERIVED

`Equipment_Combined` не является источником истины и не сохраняется как самостоятельный persisted Dataset. Его зависимости явно объявлены как `mounted`, `stationary`, `transport`, `transport_start_points`, `zabbix`. После изменения любого из этих источников Runtime Repository немедленно пересчитывает derived Dataset на synchronization barrier; несвязанные Dataset его не инвалидируют. Если обязательная зависимость отсутствует, старый derived-кэш не используется и синхронизация сообщает ошибку.

Для одновременной загрузки нескольких Equipment-источников используется атомарный REPLACE batch. Integration Engine сначала накладывает все подготовленные планы на текущее состояние источников в памяти и запускает Equipment Combined processor по полному кандидату. Затем Repository применяет исходные Dataset внутри одной `BEGIN IMMEDIATE`/transaction boundary. При любой ошибке изменения источников откатываются целиком; частично обновлённое Equipment-состояние не публикуется. Успешно рассчитанный derived-кандидат передаётся synchronization barrier и кэшируется с сигнатурой уже зафиксированных revisions, поэтому второй пересчёт после COMMIT не требуется.

## 7. Repository API

Ни UI, ни аналитические модули не должны выполнять произвольный SQL напрямую.

Единственная граница приложения с SQLite — Repository API:

- `openDatabase`;
- `createDatabase`;
- `validateDatabase`;
- `getCompatibility`;
- `migrateDatabase`;
- `getDatabaseInfo`;
- `listDatasets`;
- `getDataset`;
- `replaceDataset`;
- `upsertDataset`;
- `getImportHistory`;
- `exportDatabase`;
- `closeDatabase`.

Физические имена таблиц и SQL остаются внутри Database/Repository слоя.

## 8. Правила миграций

При открытии базы приложение проверяет `application_id`, `user_version` и полный контракт `dataset_registry` относительно текущего Dataset Catalog.

Статусы:

- текущая схема — открыть;
- поддерживаемая старая схема — требуется миграция;
- более новая схема — запрет записи;
- слишком старая неподдерживаемая схема — отказ;
- повреждённая/чужая БД — отказ.

Миграция выполняется только последовательно, без прыжков:

`N -> N+1 -> ... -> CURRENT`.

Перед изменением создаётся резервная копия исходного файла. Сама миграция выполняется транзакционно:

1. `BEGIN`;
2. выполнить migration;
3. проверить обязательные таблицы и инварианты;
4. записать `schema_migrations`;
5. обновить `PRAGMA user_version`;
6. обновить `app_metadata`;
7. `COMMIT`.

При ошибке — `ROLLBACK`. Исходная резервная копия сохраняется.

Выпущенная версия DB Schema никогда не переписывается задним числом. Любое изменение структуры создаёт новую версию и новую migration.

## 9. Атомарность интеграции

REPLACE и UPSERT выполняются только внутри SQLite transaction.

Запрещено:

- сначала удалять старый справочник, а затем отдельно загружать новый;
- частично фиксировать UPSERT;
- менять `dataset_registry` раньше успешной записи Dataset.

`dataset_registry`, `dataset_records`, `dataset_state` и запись `import_history` должны переходить в новое состояние одним commit.

## 10. Связь с текущим Dataset Store

На переходном этапе текущий Dataset Store остаётся публичной границей существующих модулей.

SQLite Core уже реализует Repository рядом с текущим Dataset Store, не меняя предметные правила существующих модулей.

Целевая цепочка:

`UI / Analytics -> Repository API -> SQLite/WASM -> Reclassifier.db`.

После перевода всех модулей старое embedded-хранилище и HTML snapshot Dataset удаляются отдельным финальным этапом.


## 11. SQLite WASM runtime

Приложение использует официальный SQLite WASM 3.53.4. На build-time принимается только release-сборка `sqlite-wasm-3530400.zip` с фиксированным SHA3-256 `e4fa7e1750b42f6954115d8e69ffff7dc08da7e9fee6e28a2a0ea6bf228a49f2`. Проверка выполняется до распаковки как для sqlite.org fallback, так и для локального offline archive. Loose-пара `vendor/sqlite/sqlite3.js` + `sqlite3.wasm` намеренно не принимается, потому что проверка версии/заголовка не подтверждает происхождение байтов. JavaScript loader и WASM-бинарник встраиваются в итоговый HTML.

В runtime:

- `sqlite3.wasm` не загружается из сети: бинарник передаётся loader как встроенный `wasmBinary`;
- OPFS/KVVFS VFS отключены, чтобы SQLite не создавал внешние proxy Worker и не зависел от HTTP-заголовков;
- рабочий файл находится во временной WASM VFS текущего запуска;
- открытие существующего `.db` переносит его байты в WASM VFS;
- каждый кандидат получает уникальное внутреннее имя `/reclassifier-N.db`; после успешной замены предыдущий файл удаляется из SQLite/WASM VFS, отклонённый кандидат удаляется сразу, а `closeDatabase()` удаляет последний активный внутренний файл;
- выгрузка сериализует SQLite обратно в обычный переносимый `.db`;
- база работает в rollback-journal (`journal_mode=DELETE`), поэтому экспорт не зависит от отдельного WAL-файла;
- SQL доступен предметным модулям только через `ReclassifierDatabaseRepository`.

В приложении 0.17.0 добавлен пользовательский раздел «Работа с базой данных»: создание/открытие/выгрузка `Reclassifier.db`, отображение паспорта БД и Dataset Registry, а также очередь нескольких Excel-файлов с распознаванием по структуре. Приём Excel остаётся недеструктивным: на этом этапе файлы не изменяют SQLite, а «Интегрировать» заблокирована до подготовки и валидации Dataset. Аналитические модули пока продолжают читать текущий Dataset Store.


## 12. Database Workspace UI

Версия 0.17.0 добавляет отдельный пользовательский контур управления SQLite.

Поддерживается:

- развернуть новую `Reclassifier.db` DB Schema 1;
- открыть существующую совместимую БД;
- показать имя файла, UUID, DB Schema, SQLite version и дату изменения;
- показать `dataset_registry`: Dataset, стратегию, Dataset Schema, число строк и свежесть;
- выгрузить текущую БД одним переносимым `.db`;
- закрыть БД с предупреждением о невыгруженных изменениях;
- загрузить несколько Excel через кнопку или drag-and-drop;
- распознать Excel по внутренней структуре через общий распознаватель справочников/ITSM/МБ/Equipment/Classifier.

Открытие или создание другой БД не закрывает текущую до успешной валидации нового экземпляра. Если новый файл повреждён или несовместим, текущая база остаётся открытой, а отклонённый VFS-кандидат удаляется. После успешной публикации нового handle прежний внутренний файл удаляется; это предотвращает накопление многосотмегабайтных временных копий в памяти текущего запуска.

Очередь Excel на этом этапе не вызывает `replaceDataset()` или `upsertDataset()`. Это сознательная граница: сначала распознавание и отображение, затем отдельный этап подготовки/валидации и только потом явная интеграция.


## 13. Dataset Recognizer

Версия 0.18.0 добавляет отдельный слой распознавания и предварительной валидации входных Excel перед интеграцией в SQLite.

Поток:

`Excel → structural recognition → full validation → key checks → freshness → readiness → integration (следующий этап)`.

Dataset Recognizer:

- определяет логический Dataset по внутренней структуре Excel, а не только по имени файла;
- показывает confidence распознавания;
- повторно использует штатные валидаторы Reference Manager, Equipment и классификатора отказов;
- отдельно проверяет полный входной контракт ITSM и Мобильных бригад;
- для UPSERT-наборов проверяет наличие и уникальность устойчивого ключа;
- считает исходные и подготовленные строки;
- определяет свежесть ITSM по «Дата создания Вызова»;
- определяет свежесть МБ по «Фактическая дата» и сравнивает её с датой в имени файла, если она присутствует;
- для Reclassification использует «Дата выполнения обращения»;
- для классификатора отказов использует «Дата изменения»;
- для Zabbix предпочитает поле `update`;
- для справочников без временной оси явно показывает, что свежесть не применяется;
- выдаёт статус `Готов к интеграции`, `Готов с предупреждениями` или `Не готов к интеграции`.

Шаг 4 не вызывает `replaceDataset()` или `upsertDataset()`. Ошибки распознавания, схемы или ключей не могут изменить подключённую БД.


## 14. Dataset Integration Engine

Версия 0.19.0 включает рабочую запись распознанных Dataset в `Reclassifier.db`.

Поток:

`Excel → Recognizer → повторная валидация → нормализация → diff → подтверждение → transaction → import_history`.

Перед COMMIT движок повторно распознаёт исходный файл и проверяет, что Dataset не изменился. Затем формируется нормализованный набор записей и вызывается `previewDatasetChange()`. План привязан к `database_uuid`: если пользователь сменил БД или содержимое БД изменилось после расчёта diff, COMMIT блокируется и план нужно пересчитать.

Стратегии:

- `UPSERT` — `itsm_data` по `number` и `mobile_brigade_data` по `recordKey`; незатронутая история не удаляется;
- `REPLACE` — Reference, Equipment source Dataset и Failure Classifier; старый набор заменяется новым внутри одной SQLite-транзакции;
- `DERIVED` — не интегрируется напрямую.

ITSM перед записью проходит штатный `PROCESS_ITSM` Worker. Все справочники и Mobile Brigade Data для его обогащения берутся из **той же подключённой SQLite-БД**. Если обязательный Dataset ещё не интегрирован в БД, ITSM блокируется с перечнем зависимостей.

Для Equipment вместе с опубликованными records сохраняется сериализованное служебное состояние `joinIndex`, чтобы последующая SQLite-миграция аналитических модулей могла восстановить связи, которые не входят в публичные колонки отдельных каталогов.

Для каждого импорта сохраняются source fingerprint, версия Dataset Schema, свежесть, количество строк и diff. Успешный COMMIT получает статус `COMMITTED`. Если исключение возникает внутри транзакции, SQLite откатывает Dataset; после rollback движок отдельно пытается записать `FAILED` в `import_history`, не маскируя исходную ошибку.

DB Schema остаётся **1**: шаг 5 использует уже предусмотренные `dataset_records`, `dataset_state`, `dataset_registry` и `import_history`, поэтому структурная миграция БД не требуется.

Граница этапа: SQLite уже является рабочим целевым хранилищем для Database Workspace, но остальные аналитические страницы приложения пока продолжают читать старый Dataset Store. Их переключение на Repository API выполняется отдельным этапом.


## 15. Контроль интеграций и журнал

Версия 0.20.0 добавляет наблюдаемость поверх уже существующих таблиц DB Schema 1. Структура БД не меняется.

Источник контроля — только SQLite:

- `dataset_registry` — текущее активное состояние Dataset: revision, record_count, freshness, source file, updated_at;
- `import_history` — все попытки интеграции и их diff;
- `getImportOverview()` — Repository API для сводных показателей по всей истории, а не только по видимым строкам журнала.

`getImportOverview()` возвращает:

- общее число попыток;
- число `COMMITTED`;
- число `FAILED` / `ROLLED_BACK`;
- дату последнего успешного импорта;
- дату последней ошибки;
- последнюю попытку в целом;
- последнюю попытку по каждому Dataset;
- последний успешный импорт по каждому Dataset.

Последняя попытка по Dataset выбирается SQL-окном `ROW_NUMBER() OVER (PARTITION BY dataset_id ...)`, поэтому результат остаётся корректным даже при большой истории. Сам журнал по-прежнему читается через `getImportHistory()`; UI запрашивает до 1000 записей и фильтрует их по Dataset и статусу.

В карточке Dataset показываются:

- текущий источник;
- strategy / Dataset Schema;
- record_count и active revision;
- freshness;
- последний успешный импорт;
- последняя попытка и её статус;
- последний diff;
- время изменения активного Dataset.

Журнал интеграций показывает:

- время;
- Dataset;
- статус;
- файл-источник и стратегию;
- rows_before / rows_incoming;
- rows_inserted / rows_updated / rows_unchanged / rows_deleted;
- rows_after;
- App Version / DB Schema / Dataset Schema;
- message и `details_json`.

Ошибочная попытка не меняет `dataset_registry` и активные записи Dataset, но сохраняется в `import_history`, поэтому оператор видит ошибку без искажения фактического состояния данных.

DB Schema остаётся **1**.


## 16. SQLite-first runtime repository

Версия 0.21.0 переводит чтение рабочих Dataset на Repository API.

Цепочка:

`UI / Analytics → ReclassifierRuntimeDataRepository → ReclassifierDatabaseRepository → SQLite/WASM → Reclassifier.db`.

Runtime repository имеет два режима:

- `legacy` — если SQLite-БД не открыта; чтение идёт из прежнего Dataset Store и встроенного HTML-baseline;
- `sqlite` — если открыта валидная `Reclassifier.db`; SQLite становится единственным авторитетным источником.

В SQLite-режиме отсутствующий Dataset возвращается как отсутствующий. Runtime **не** подмешивает соответствующий Dataset из HTML-baseline, потому что смешивание двух независимых состояний давало бы недетерминированные результаты аналитики.

SQLite Dataset адаптируется к существующему runtime-контракту `{ id, records, validation, meta }`. В `meta` публикуются source file, Dataset Schema, active revision, freshness, content hash, database UUID и признак `sourceType = sqlite`.

Для Equipment сериализованный `joinIndex` восстанавливается из `dataset_state`. `Equipment_Combined` не хранится как источник истины: в SQLite-режиме он динамически пересчитывается из пяти текущих Equipment source Dataset. Если полного набора источников нет, Combined считается недоступным.

Крупные Dataset кэшируются в runtime. Кэш очищается:

- после создания/открытия БД;
- после успешного REPLACE/UPSERT;
- после закрытия БД.

Так повторные обращения ITSM/МБ не требуют повторного JSON-парсинга всех строк.

Чтобы не возникало расхождения «SQLite показывает одно, старый Dataset Store — другое», при активной БД `datasetPipeline.setActive()` запрещает применение legacy-кандидата. Пользователь может продолжать обрабатывать/скачивать Excel в предметном модуле, но сохранять рабочий Dataset нужно через Database Workspace.

DB Schema остаётся **1**: изменение касается runtime-доступа, а не физической структуры SQLite.


## 17. Переносимость и целостность

Версия 0.22.0 усиливает переносимость DB Schema 1 без изменения физической схемы.

Repository API добавляет `runHealthCheck()`.

Проверка возвращает:

- результат структурной валидации Reclassifier DB;
- SQLite `quick_check`;
- `foreign_key_check`;
- расхождения `dataset_registry.record_count` и фактического количества `dataset_records`;
- отсутствующие обязательные Dataset Registry;
- `journal_mode`;
- page_count / page_size и оценочный размер файла;
- время выполнения;
- список ошибок и предупреждений.

База считается переносимой только если:

1. application_id / user_version / app_metadata корректны;
2. `quick_check = ok`;
3. foreign key нарушений нет;
4. Dataset Registry согласован с records;
5. обязательные Dataset зарегистрированы;
6. `journal_mode = DELETE`.

`openDatabase()` выполняет integrity check на временно открытом новом handle **до** закрытия текущей базы. Поэтому повреждённый или неконсистентный файл не разрушает текущую пользовательскую сессию.

`exportDatabase()` выполняет полный health check до получения байтов. Если проверка не пройдена, экспорт блокируется. После экспорта проверяется стандартный заголовок `SQLite format 3\0`.

CI дополнительно выполняет реальный файловый round-trip средствами SQLite: DB Schema 1 → Dataset records/state/import_history → close → byte-for-byte copy → reopen read-only → quick_check / foreign_key_check / application_id / user_version / business rows. Повреждение заголовка отдельного файла должно приводить к ошибке SQLite.

Портативность HTML контролируется существующим offline regression: FULL artifact должен оставаться меньше 50 MiB, CSP и network guard запрещают сеть. Browserless startup/runtime smoke имеет регрессионный лимит 10 секунд.

DB Schema остаётся **1**.


## 18. Первичное развёртывание из HTML

Версия 0.22.1 меняет смысл операции создания базы:

`HTML Dataset Store → bootstrap snapshot → SQLite transaction → Reclassifier.db`.

`ReclassifierDatabaseBootstrap.collectSeeds()` снимает активное состояние всех persisted Dataset до открытия новой SQLite-БД. Это важно, потому что после создания БД runtime переключается в SQLite-authoritative mode и legacy Dataset Store больше не должен участвовать в рабочих чтениях.

`ReclassifierDatabaseRepository.bootstrapDatasets()` разрешён только для новой базы, у которой нет активных revision. Все Dataset записываются в одной транзакции `BEGIN IMMEDIATE … COMMIT`. При любой ошибке выполняется `ROLLBACK`.

Запись выполняется пакетами по 1000 строк с yield между пакетами, чтобы браузер мог обновлять progress UI. Для UPSERT Dataset используются штатные устойчивые ключи (`number` для ITSM, `recordKey` для Mobile Brigade). Для REPLACE Dataset формируются стабильные row-keys. Сохраняются source file, fingerprint/content hash, freshness и `dataset_state`, включая Equipment `joinIndex`.

В `import_history` каждый стартовый Dataset получает отдельную запись `COMMITTED` с причиной «первичное развёртывание из встроенных Dataset HTML».

После bootstrap выполняется полный health check. `Equipment_Combined` не сохраняется: он остаётся `DERIVED`.

UI различает три операции:

- **Развернуть БД из HTML** — создать новую БД и перенести стартовые Dataset;
- **Открыть существующую БД** — подключить ранее сохранённый SQLite-файл;
- **Скачать Reclassifier.db** — экспортировать текущую активную БД после проверки целостности.

Переход между разделами приложения не закрывает активную БД. Видимая кнопка «Закрыть» удалена; внутренний `closeDatabase()` остаётся частью Repository API для безопасной замены БД и обработки ошибок.

DB Schema остаётся **1**.


## 19. Память при больших Dataset

Версия 0.22.3 сохраняет DB Schema 1. Для UPSERT preview и commit больше не читают целиком ранее сохранённый JSON Dataset: индексированный поиск по `PRIMARY KEY(dataset_id, record_key)` выполняется для каждой входной строки, а в JS хранится только Set входных ключей. Это устраняет два пиковых копирования текущих 50k+ ITSM записей. После успешной транзакции Integration Engine сверяет revision и count через `getDatasetRegistry`, а не через `getDataset`.

Номера заявок из распознанного ITSM передаются в `getMobileBrigadeRowsForRequests`. Этот метод итерирует SQLite statement построчно и выдаёт в Worker только совпавшие задачи МБ. Полный набор МБ для других runtime-модулей остаётся доступным через Repository API.

Подтверждение вынесено из системного `confirm` в явные кнопки интерфейса, так как подавленный браузером модальный диалог не должен имитировать решение пользователя. Health check после большого COMMIT выполняется отдельно по кнопке, немедленная проверка количества строк — чтением registry.

Диагностика памяти/диска: health check вычисляет `SUM(LENGTH(CAST(record_json AS BLOB)))` по Dataset без материализации в JS. Эти значения показывают объём исходного несжатого payload; физический размер SQLite больше из-за страниц и индексов. Пока JSON хранится без compression, переносимый `.db` не обязан быть сравним по размеру со сжатым FULL HTML. Принятие сжатой физической схемы — отдельное архитектурное решение.


## 20. Стресс-устойчивость и прерываемая интеграция (0.23.0)

- `ReclassifierDatabaseIntegration.prepare` вызывает для ITSM Worker режим `datasetOnly`: 17 исходных и 34 расчётных поля формируются, но выходной XLSX не записывается. Публичный режим ITSM сохранён без изменений.
- `upsertDatasetAsync` держит одну SQLite `BEGIN IMMEDIATE` транзакцию с SQL-поиском по составному ключу `(dataset_id, record_key)`. После каждых 250 входных записей отдаёт прогресс и уступает браузеру event loop. Публичная граница Repository защищена единым operation mutex: пока async-операция владеет SQLite handle, любой второй публичный read/write/export/close вызов завершается явной ошибкой `RECLASSIFIER_DATABASE_BUSY`. Это запрещает чтение незакоммиченного состояния и замену/закрытие handle между batch-yield. Запрос отмены проверяется до записи и перед COMMIT. При исключении выполняется `ROLLBACK`, затем отдельная транзакция добавляет запись аудита `FAILED` или `ROLLED_BACK`; активный Dataset и его revision не должны измениться.
- Предварительный diff остаётся невлияющим на базу. Реальная запись защищена проверкой UUID и версии Dataset Registry непосредственно перед транзакцией. Повторный ввод того же содержимого не должен менять записи, хотя успешная попытка отражается в журнале и revision.
- SQLite `.db` проверяется по размеру и первым 100 байтам до дорогостоящей загрузки в RAM, а неудачное открытие не закрывает предыдущую базу. Максимальный поддерживаемый размер входного файла в HTML-версии: 1 ГиБ; фактический лимит RAM зависит от браузера и устройства.
- Реальные SQLite WASM-тесты отдельно проверяют откат прерванного первичного bootstrap, позднего дублирующего ключа, прерывание и повторный UPSERT, экспорт / повторное открытие, заголовок повреждённого файла, а также сохранение 50 331 строк стартового ITSM.
- Отдельная локальная Chromium acceptance-проверка открывает CORE HTML непосредственно по `file://` с включённым browser offline mode и проверяет создание, сохранение и повторное открытие синтетической пользовательской SQLite. Она не требует корпоративной базы и не подтверждает её бизнес-содержимое.


## 21. Заключительный контроль архитектуры (0.24.0)

`Repository.hasOpenDatabase()` — отдельный от валидности metadata API. При открытом дескрипторе ошибки SQLite metadata/registry/record_count не должны маскироваться переключением в HTML baseline. При закрытом дескрипторе HTML Dataset Store остаётся рабочим автономным режимом; его применение запрещено в активном SQLite. Формирование/восстановление HTML snapshot возможно только в режиме без БД. Состояние `Equipment_Combined` вычисляемое, не persisted. Проверки включают автоматическую смену режимов, полноценный file:// offline browser и round-trip большой БД.
